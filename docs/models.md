# glTF gun models

Every gun the game shows (first person, third person, the gunsmith, the hangar, icons, loot) is a baked glTF: every part's pieces, baked once, assembled for any build at run time by a few rules (`js/glb.ts`), behind the synchronous facade `js/gunmodels.ts`. The procedural **recipes** that make them are bake-time code only (`tools/models/*.ts`, compiled by `tsconfig.tools.json`); the game loads none of them and has no fallback to them: a build the pieces do not cover just stays empty (a baker bug, not something to patch at run time). Milestone 1: whole default guns (no longer baked unless asked: `--guns`). Milestone 2: per-part packs and runtime assembly of any build. Milestone 3: the per-part bake (below): no combination of parts is baked.

## Loading (no flags)

- **GLTF loader.** three's own `GLTFLoader` and meshopt decoder, from the same pinned three as the page (`js/threeboot.ts`, the one module the page loads, imports them from jsDelivr's builds, whose `import 'three'` points at that same three, and sets a global `ThreeAddons`); js/glb.ts makes `G.GLB = { ready, load(url) }` from it. The highlights export worker imports the same module before its `importScripts`; `G.Models.setRoot('../../')` tells it where the game's folder is from `dist/js/`.
- **One bundle, downloaded at boot.** The game never fetches a loose model file: `js/modelbundles.ts` (`G.Bundles`, the FIRST script in index.html, before three.js) downloads ONE file, `assets/models/bundles/models.rtb` (every pack, platform index and prop; see "Bundles" below), the moment the page loads, beside the main menu, and keeps it in memory. `js/glb.ts` slices the pack, index or prop out of it. Nothing waits on a model fetch later.
- **Menu and the models.** The menu is usable at once and shows the download (`#modelLoad`: bytes, then "Models ready"; a failure, after three attempts, says so with a Retry button: there is no partial play). What enters the game (Host, Play Solo, Join, the highlights video) waits for the bundle (`G.Game.needModels`: it says so and goes on by itself when the models are in); the rest of the menu does not. Data saver and 2g are not special-cased: the game cannot be played without its models, so they are fetched in any case (one request, ~3.2 MB gzipped, once per deploy: the local store keeps it).
- **Boot parsing** (`G.GunModels.boot()`, js/game.ts `init`): every platform's `parts/<id>/index.json` and the props are parsed from the bundle (JSON, no glTF); with the index a gun's `info` (anchors, muzzles, sight windows, mounts) is known without any pack: `G.Models.infoFromIndex(def)`. **Glbs are never parsed at boot**: a pack is parsed when a model is first shown (`G.Models.ensure(def)`, the facade's `display` / `world` / `viewmodel`), and the parsed result is kept.
- **The parse queue.** Pack parses go through one priority queue (`js/glb.ts`): 0 = needed now (a gun on screen, the squad's kits), 1 = wanted soon (the level's enemy pool as default builds, the gunsmith's platform), at most 8 at once. There is no background tier and nothing is fetched: it only schedules main-thread glTF parsing. The gunsmith opens a gun's whole platform; a level's start parses the squad's builds and the enemy pool's default builds (no whole platforms); anything else is parsed when first asked for. A missing pack never throws.
- **The main menu's backdrop** (a level built behind the menu) is built after the first paint, in two tasks, and after the bundle is in memory (1.2 s at most): see "Boot freeze" under Bundles.
- `?checkModels`: validates each model in the browser as it loads (console errors and warnings).

### The facade: synchronous, filling in

`G.GunModels.display(def, skin)` / `world(def, skin)` / `viewmodel(def, skin)` (js/gunmodels.ts) are synchronous for their callers. If the build's packs are loaded the model is whole. If not, `display` and `world` return an EMPTY group with `userData.pending = true` and the right `info` (from the platform's index), and the meshes arrive in it when the packs do (`world`'s merged meshes, magazine, a crossbow's bolt and strings, a bipod's legs too). `G.GunModels.whenReady(group, fn)` calls `fn(ok)` then (at once if it is not pending): icons (the `gunicons` window event redraws the screens that showed an empty cell), the gunsmith's framing, the hangar's part stands, loot's resting place, a highlight's gear stage and the evidence outline all use it. `viewmodel()` cannot be empty (the hands are bound to the gun's parts): it returns `null` until the build is loaded (and asks for it); `js/player.ts` sets the view model each frame it is not the right one, so it appears the frame it can.

### Props: cartridges and the crossbow bolt

`npm run bake:props` (`tools/bake_props.mjs`, also run by `bake:models`) writes `assets/models/props/round_<caliber>x<case>.glb` (a cartridge: `body`, `rim`, `bullet`, or `case`, `bullet` for the .50 BMG's real profile), `round_shotshell.glb` (`hull`, `base`), `quarrel.glb` (the crossbow bolt, centred: `nock`, `shaft`, `vanes`, `head`) and `index.json` (`rounds`: gun id -> round key; `keys`: file, `dims` (head, case length, bullet length/diameter, shell, pistol) and, for the BMG, `shape`). The game reads them: `G.GunModels.roundDims(def)`, `roundShape(def)`, `roundProp(def, 'shell' | 'case')`, `quarrel()`.

## Layers: geometry, rig, first-person extras

A gun model is three separate things, each working on the model (nodes + extras), not on how it was made:

| layer | where | what it does |
| --- | --- | --- |
| geometry | a `.glb` (`js/glb.ts`; the recipes in `tools/models/recipes.ts` make them, at bake time) | slot-tagged meshes, `part_<key>` nodes with their pivots, `info` |
| rig | `js/gunrig.ts` | `G.GunRig.bind(group, info, { def, side })`: finds the moving parts (`info.anim`: nodes, or the node names of a loaded file), the hand anchors in the gun's space, where the parts rest, the magazine-check data. `js/vmanim.ts` (the clips) reads nothing else off the gun |
| first-person extras | `js/viewmodel.ts` | `G.Viewmodel.assemble(def, models)`: a reflex sight's reticle (`info.reflex`), a scope's lens (`info.pip`), muzzle flashes (one per `info.muzzles`), `display_<name>` surfaces (a CanvasTexture each: `G.Viewmodel.surfaces(group)`), then the rig and arms. And `worldProto` / `worldInstance`: the third-person model, merged one mesh per material, with the magazine, a crossbow's bolt and strings and a bipod's legs pulled out |

`G.GunModels.viewmodel(def)` / `world(def)` / `display(def)` only fetch geometry (assembled from the packs) and hand it over; the first person's stock is clipped near the eye at render time (js/render.ts). A bipod is a `part_bipod` node whose child groups are its legs, with the folded and the deployed pose as data (`extras.leg.deploy`; the contract's "Bipods"): `G.GunRig.bipodPose(node, k)` turns them, for the first person (the live node, `an.bipod`) and the third (`worldProto` pulls each leg out; `worldInstance` gives a node `userData.bipod` of the legs). The first person's reflex and scope windows are `info.reflex` / `info.pip`; a magnifier's lens hangs on its `part_magn` node and a crossbow's lit nock gets a material of its own, both done by `viewmodel()`.

`bake_models.mjs` calls `G.GunRig.describe(group)` first: a recipe's magazine-check data is meshes held by reference, which a file can't carry, so it is written down as tags on the nodes (see "Magazine check" in the contract). An AUTHORED source's magazine already has the tags (part_mag `extras.check`, its meshes' `extras.chk`): `tools/bake_authored.mjs` reads them, and keeps each tagged mesh's geometry in its own node's frame with that node's place and rotation (a witness hole is tilted to the face there), and the recipes place each as a mesh of its own with the tag and put the check on the magazine's part node, so the packs carry them as a recipe's do (`tools/check_authored_magcheck.test.mjs`: the recipe's and the baked magazine of every source that has them).

## The contract

**The contract is code**: `GUN_MODEL_CONTRACT` and `INFO_FIELDS` in `js/glb.ts`. Everything else is generated from it, or checked against it:

- `validate()` (the same function in node and the browser; it works on a plain description of the node tree, `describeGltfJson` for a `.glb`'s JSON, `describeScene` for a loaded scene) is used by the baker, by `check:models`, and by `?checkModels`;
- `docs/gun-model-info.schema.json` is the JSON Schema (draft 2020-12) of the root `extras.info`, for a loader or exporter written in anything else (a Rust/Bevy loader can read this plus the tables below without reading TypeScript). It is generated, and `test:models` fails when it differs from `INFO_FIELDS`;
- the tables below are generated between the markers (`check:models -- --write`), and `test:models` fails when they drift;
- the TypeScript interface `GunModelInfo` and `INFO_FIELDS` are tied by a mapped type: a field in one and not the other does not compile; the material list is compared with `G.GunMaterials.M` (js/gunmaterials.ts) by `test:models`.

### An example node tree (an M4, abridged)

```
scene
└─ m4                         extras { gun: "m4", info: { sy, fSight, relief, muzzles: [[0.595,0,0]], grip, support, anim: { mag: "part_mag", ch: "part_ch" }, magAt, ... } }
   ├─ base_1 ... base_80      meshes, extras { slot: "base" }, material "black" / "polymer" / ...
   ├─ grip_81 ...             meshes, extras { slot: "grip" }, material "stipple"
   ├─ part_ch                 extras { part: "ch" }: the charging handle, pivot at its node origin
   │   └─ charging_90         extras { slot: "charging" }
   ├─ part_mag                extras { part: "mag" }: the magazine, drops out on a reload
   │   └─ mag_91 ...          extras { slot: "mag" }
   └─ optic_100 ...           extras { slot: "optic" }
```

### Display surfaces and part-provided anchors, in short

A mesh `display_ammo` (extras `{ slot, display: { width: 128, height: 32 } }`, **with UVs**) is a surface the game paints with a CanvasTexture; its material is left alone by the loader. A `part_<key>` node (or the root of a per-part pack) may carry `extras.anchors` (`{ muzzles: [...], mount_muzzle: [...] }`) in its own frame; assembly moves them into the gun's frame and merges them into `info`: `muzzles` is the concatenation of every providing part's list (a barrel block provides N), a frame's `mount_<slot>` lands in `info.mounts`, any other anchor is overridden by the later provider. `muzzles` may have several entries: consumers must never assume `[0]` is the only one. The full rules are in the tables.

### The contract, generated

<!-- contract:begin (generated by npm run check:models -- --write: edit js/glb.ts, not this) -->
**Frame.** Metres. The glTF frame (x = right, y = up, z = -forward) with the origin at the gun's own origin (the point the recipe builds around: roughly the back of the receiver on the bore line). Every anchor in `info` is written [forward, up, right] = [-z, y, x]; a node's transform is in the same frame, so a part is built "in place" and its node origin is only its pivot.

**Node tree.**

- root: The scene has exactly ONE root node, named after the gun id (e.g. "m4"). Its extras are { info: <GunModelInfo>, gun: <the same id> }. It has no transform.
- meshes: Every mesh node is named "<slot>_<n>" (n unique in the file), has extras.slot = a SLOTS value, and one material from the catalogue. Meshes sit directly under the root, or inside a part_ / group_ node; the baker welds and quantises but never joins meshes.
- parts: Every animated sub-assembly is a node "part_<key>" (a PARTS key) with extras.part = <key>, holding its meshes; its origin is the pivot (hinge or slide point). Each is listed in info.anim.<key> by node name; a part_ node that isn't listed, or a listed one that's missing, is an error.
- groups: Any other grouping node is named "group_<n>".

**Display surfaces** (`display_<name>`):

- naming: A mesh node named `display_<name>` (name: lower-case letters/digits/underscores, e.g. `display_ammo`) is a display surface: the game paints it at runtime with a CanvasTexture (the way reflex reticles are drawn), so the model only says where and how big. It still needs extras.slot (the part it belongs to) like any mesh.
- UVs: It MUST have UVs (TEXCOORD_0, covering the 0..1 square: the canvas is mapped across it, u right, v up). A display without UVs is an error.
- size: extras.display = { width, height } in pixels: the canvas resolution the game should draw at (a hint, powers of two preferred); width / height is the intended aspect ratio of the surface, so author the UVs un-stretched for it. Required.
- material: The loader does NOT swap its material for a catalogue one (any material name is accepted, `display` suggested): the game replaces it with the canvas texture's material. Everything the loader does to other meshes (catalogue materials, bump maps) is skipped for it.
- example: `{"name":"display_ammo","extras":{"slot":"barrel","display":{"width":128,"height":32}}}`

**Anchors a part provides** (`extras.anchors`):

- where: A node may carry `extras.anchors`: positions it PROVIDES, in the node's OWN frame (the same [forward, up, right] metres, measured from the node's origin along its axes; a part's mesh positions are in that same frame). Allowed on `part_<key>` and `group_<n>` nodes, and on the root of a per-part pack (a .glb holding one swappable part). Keys are the info anchors a part can provide (muzzles, grip, support, magAt, port, ch, bolt, slide, cylAt, cup, cheek, chamberAt) or a mount point `mount_<slot>` (a [forward, up, right] vec3; e.g. mount_muzzle on a frame says where a muzzle device sits).
- Assembly (the per-part pieces follow the same rules: GUN_MODEL_CONTRACT.packs; the rule applies to the node tree of a whole-gun file) starts from the receiver's `info` and visits the parts in the gunsmith's slot order.
- Every provided position is first moved into the gun's frame: the providing node's transform in the assembled gun applied to the position (the part's placement), then re-expressed as [forward, up, right] = [-z, y, x].
- `muzzles` is a LIST built from whichever parts provide it: if any part provides `muzzles`, the gun's `info.muzzles` is the concatenation of those parts' lists (tree order) and the receiver's own default is dropped; if none does, the receiver's is kept. A barrel block with 6 barrels provides 6 muzzles.
- `mount_<slot>` anchors are OFFSETS: the displacement [forward, up, right] metres of the part in <slot> from where its piece sits when no part offsets it (no offset from the provider itself: GUN_MODEL_CONTRACT.packs offsets). Every provider's offsets for a slot ADD UP (a barrel and a handguard may both move a light); the sum is `info.mounts.mount_<slot>` and the whole part moves by it.
- Every other anchor (grip, support, magAt, port, ch, bolt, slide, cylAt, cup, cheek, chamberAt) is single-valued: a part's value overrides the receiver's and an earlier part's (the last provider in slot order wins; the validator warns when two parts of one gun both provide it).
- muzzles: A gun can have MORE THAN ONE muzzle (an over/under, a Metal Storm-style barrel block): `info.muzzles` is always a list of at least one [forward, up, right]; consumers must iterate it and never assume entry [0] is the only one.
- example: `{"name":"part_barrel","extras":{"part":"barrel","anchors":{"muzzles":[[0.4,0.012,-0.012],[0.4,0.012,0.012]],"mount_muzzle":[0.4,0,0]}}}`

**Authored sources** (a gun modelled in Blender, baked with no recipe):

- what: AUTHORED SOURCE. A gun modelled in Blender is baked straight from its .glb with no recipe (tools/bake_authored.mjs, `npm run bake:models`). The source is models/<id>/<id>.glb plus models/<id>/model.json ({ "source": "authored", "sights": { "builtin": [<optic kinds that mean the gun's own sights>], "rail": [<of those, the ones that still sit on a rail piece: a riser>] } }); the model is the authority for everything it holds, and a gun without model.json keeps being built by its recipe. `npm run check:models -- models/<id>/<id>.glb` validates a source (validateAuthored).
- nodes: The scene has one root node named after the gun. Its children are the base (receiver) and the gun's FACTORY parts, as meshes "<slot>_<n>" with extras.slot (the contract's slots) and a catalogue material: the base is every mesh of slot base that is not in a part_ node; the stock, grip, handguard, barrel, muzzle and optic (the irons) meshes are the parts the gun's default build fits, and the model must hold meshes for every slot the default build fills; the magazine is the node part_mag with its meshes (slot mag), the charging handle part_handle (slot base); every moving part is a part_<key> node (contract parts) with its pivot at the node origin and listed in info.anim. A factory part's id is the platform's (js/parts.ts), not written in the model.
- info: Root extras.info (or the JSON text info_json): the factory build's info, exactly INFO_FIELDS (sy, fSight, relief, muzzles, grip, support, anim, magAt, handle, port, chamberAt, ...).
- anchors: Root extras.anchors (or anchors_json): the gun's MOUNT ANCHORS, [forward, up, right] metres in the gun's frame, the places the gun's non-factory parts are seated on. Every part the gun accepts that is not one of the model's own is built at its own designed size and placed on these, never stretched: the table lists them. A `_end` anchor is the far end of a span. Further `mount_<slot>` anchors (a side rail: mount_tac, mount_tacL) are allowed and are carried into info.mounts.

| anchor (extras.anchors) | meaning |
| --- | --- |
| `mount_optic` (required) | the START of the optic rail on the receiver: [forward, the receiver's top height, 0]. A rail piece is built over mount_optic .. mount_optic_end when a real optic (or one of sights.rail) is fitted; an optic sits on it by the platform's spec (optF). |
| `mount_optic_end` (required) | the END of that rail: [forward, top, 0]. Same height as mount_optic. |
| `mount_handguard` (required) | where a handguard starts (the barrel nut's front): [forward, up, 0]. The platform's spec L is this forward value. |
| `mount_handguard_end` (required) | the furthest forward a handguard may reach (the gas block's rear): [forward, up, 0]. A handguard longer than mount_handguard_end - mount_handguard - 3 mm is not offered for the gun (the platform's spec hgMax in js/parts.ts says so; the baker checks they agree). Nothing is clamped. |
| `mount_muzzle` (required) | where the factory barrel ends and a muzzle device screws on: [forward, up, 0]. Another barrel's end is this plus its length difference from the factory one; the factory muzzle device (slot muzzle) is modelled to start here. |
| `mount_barrel` (required) | where the factory barrel begins (the start of the slot barrel meshes, ahead of the last fixed fitting): [forward, up, 0]. Slot barrel holds only the factory barrel itself, which any other barrel replaces whole: its fixed fittings (gas block, gas tube, sight base, bayonet collar) are slot base, and stay when another barrel is fitted. Another barrel is the shared one of its length and profile, ending where that length ends from mount_muzzle (nothing in the model is resized). |
| `mount_stock` (required) | where a stock is seated: [0 or the receiver's back, the centre height of the wrist at the receiver's back, 0]. |
| `mount_grip` (required) | where a grip is seated: [forward of the grip's front, the height of the receiver's underside, 0]; the grip hangs from that height. |
| `mount_mag` (required) | the magazine well: [forward, up, 0] of the top of a magazine seated in it (equal to info.magAt). |
| `mount_optic_rail` (optional) | the START of the rail on the gun's own optic mount (opticMount below): [forward, the rail's top, 0]. Required with an optic mount, allowed only with one. |
| `mount_optic_rail_end` (optional) | the END of that rail: [forward, top, 0]. Same height as mount_optic_rail. |

- opticMount: THE GUN'S OWN OPTIC MOUNT. A receiver with no rail takes a rail sight on an adapter of its own (the MP5's claw mount: a Picatinny rail on clamps whose claws hook into recesses in the receiver). The model holds it as meshes of slot optic with extras.mount = true (outside any part_ node): they are drawn, as the optic's mount piece (optic@mount), whenever a real optic or one of sights.rail is fitted, INSTEAD of the generic rail piece over mount_optic .. mount_optic_end, and never with the gun's own irons (they are not the irons: nothing looks through them). The sight stands on the adapter's rail top at the platform's optF: mount_optic_rail .. mount_optic_rail_end is that rail, its height is the top the optic's foot rests on (so info.sy follows it), and optF must lie on it (the baker checks). mount_optic / mount_optic_end stay the receiver's top under it.
- pistol: AUTHORED PISTOLS. A pistol (root extras.info.pistol = true) uses the pistol anchor set instead of the rifle one: REQUIRED mount_barrel (where the factory barrel/suppressor begins) and mount_mag (= info.magAt); mount_slide ([the slide's rear, the frame's slide seat height, 0]) when the pistol has a slide (info.anim.slide = part_slide); and, for each thing the platform lets you fit, the anchor the part is seated on: mount_optic (+ mount_optic_end, equal: the optic cut's centre on the slide's top, [forward of the slide's rear, the cut's floor, 0]; a pistol sight sits there), mount_tac (a light or laser under the frame: [forward, the underside, 0]), mount_grip, mount_stock (optional). The muzzle is info.muzzles[0]. The slots are the same as a rifle's: the frame is slot base (a slide, an action knob or a control that moves is a part_ node), the slide is slot slide in part_slide, the barrel slot holds the whole barrel/suppressor with its front sight, the grip slot (when the grip is a part), mag in part_mag, optic the rear sight and the optic cut's cover plate. A slideless pistol (a manually cycled one) moves its bolt in part_bolt (info.anim.bolt) and the model carries info.bolt, the knob the hand takes. The same rules as a rifle's otherwise: the platform in js/parts.ts says which of those anchors it uses and the baker checks they agree (mount_optic against the pistol's optic cut, mount_mag against its spec).
- variants: AUTHORED VARIANTS. A per-gun part modelled beside the gun: models/<id>/<name>.glb (any other .glb in the gun's folder than <id>.glb), offered on that gun only. ONE root node named <id>_<name> whose extras.variant_json is { gun: <id>, slot: "barrel" | "mag", of: "factory", info?: { muzzles, mounts? }, cap?: <rounds>, note }: gun is the folder, slot the slot it replaces, of the part it replaces (the factory one); info.muzzles is the new muzzle position (a barrel), info.mounts.mount_optic ([forward, up, right] metres: the centre and floor of a pistol optic cut the barrel carries, where a pistol dot is seated; the platform variant part then PROVIDES the optic slot, which only this barrel opens), cap the new capacity (a magazine). Whether the barrel is suppressed is the platform data on the part (js/parts.ts set.sup / device), not the model. The meshes are in the gun's own frame, all of slot <slot> with catalogue materials (a magazine is one part_mag node with the pivot of the factory one); nothing else. The platform in js/parts.ts adds the part (id <id>.br.<name> / <id>.mag.<name>, its figures proposed there) and the recipe draws these meshes while it is fitted; nothing is scaled.
- seat: There is no seat: another barrel is drawn from its own part (a standard radius and profile). Root extras.seat and a mesh extras.role are no longer defined and are ignored if a file still has them.
- mesh: Every mesh of slot barrel is the factory barrel, drawn only while the platform's own barrel is fitted; a fixed fitting on the barrel is a mesh of slot base.
- A gun's default build is its factory parts, taken from the model while they are fitted; every other part the gunsmith offers for the gun is the shared part for its slot, seated from the anchors above, so the same part is the same shape on every gun and on this one.
- The model's own sights: an optic kind listed in model.json sights.builtin means the gun's own irons (the optic slot of the model: the rear sight on the receiver and the front sight on the barrel). A kind also listed in sights.rail (a riser) puts a rail piece between mount_optic and mount_optic_end over them.
- A PISTOL (info.pistol) has the pistol anchor set (the pistol entry above) and no rail, handguard, stock or grip anchors beyond what the platform fits.
- Fit is data, not geometry: whether a part fits the gun is decided by js/parts.ts (fitsSlot, hgRoom with hgMax) from the platform's spec; the baker checks the platform's spec (L, hgMax, mag) against the anchors and fails when they disagree.
- example: `{"name":"fal","extras":{"gun":"fal","info_json":"{\"sy\":0.04,...}","anchors_json":"{\"mount_optic\":[0.0141,0.0232,0],\"mount_optic_end\":[0.1791,0.0232,0],\"mount_handguard\":[0.3012,0,0],\"mount_handguard_end\":[0.5357,0,0],\"mount_muzzle\":[0.7329,0,0],\"mount_barrel\":[0.6153,0,0],\"mount_stock\":[0,-0.01835,0],\"mount_grip\":[0.0661,-0.0452,0],\"mount_mag\":[0.2232,-0.0429,0]}"}}`

**Authored parts** (a shared attachment modelled in Blender: sights, prisms, scopes; furniture: stocks, grips, muzzle devices, handguards; and flip magnifiers):

- what: AUTHORED PART. A shared attachment modelled in Blender (a sight, a prism, a scope; or a piece of FURNITURE: a stock, a grip, a muzzle device, a handguard) is baked straight from its .glb: models/parts/<slot>/<id>/<id>.glb plus models/parts/<slot>/<id>/model.json. It is ONE object, the same file on every gun whose mount takes it; everything gun-specific under it (the rail section, a riser) is the gun's mount piece (tag `optic@mount`), never part of the model. `npm run check:models -- models/parts/<slot>/<id>/<id>.glb` validates one; `npm run check:models -- --write` regenerates its catalogue entry.
- frame: THE PART'S OWN FRAME. Metres, the glTF axes (x right, y up, z = -forward); anchors are written [forward, up, right] = [-z, y, x] like everywhere in the contract. Each slot has its own frame name and origin (furniture below); for an optic ("rail-top") the ORIGIN is on the top of the rail, at the optic's mount point, centred (right = 0): the plane the optic's foot rests on, so no vertex is below y = 0 (the rail, riser or adapter is the mount piece's). The recipe places it at the gun's rail top and the platform's optic position (spec optF) and the baker finds that it only translates.
- model: The .glb has ONE root node named after the part (the folder name), no extras.info and no part_ nodes; its children are meshes "<slot>_<n>" (the slot's name: optic, stock, grip, muzzle, handguard) with extras.slot and a catalogue material name (or display surfaces, as in the contract). Triangles outside the sight: none. Geometry limits for an optic: within 0.12 m either side of the origin forward and 0.04 m left/right, up to 0.15 m high.
- config: model.json: { "source": "authored", "kind": "part", "slot": "optic", "frame": "rail-top", "optic": { sy, fSight, relief, reflex?, pip?, magnifier?, height }, "part": { mount, brand, name, price, tier, zoom, st, desc?, scoped?, reticle?, px?, levels? } }. The catalogue id is derived: `op.auth.<id>`. A REPLACE-ONLY part has "replaces": [entry names] instead of "part" (see rules). FURNITURE (stock, grip, muzzle, handguard): { "source": "authored", "kind": "part", "slot", "frame": "<slot>-mount", "anchors": { ... }, "part": { the slot's data }, "replaces": [entry names or matches] }: always replace-only, "part" is the model's own data (not a catalogue entry) and the anchors are the slot's (furniture below).
- optic.sy: Height of the line of sight above the origin, metres (info.sy = the rail top + this). A reflex window's centre height must equal it.
- optic.fSight: Forward position of the sight's rear/eye reference, metres from the origin (info.fSight = the mount point + this); with relief it places the aiming eye.
- optic.relief: Eye relief, metres (0.03 to 0.4); on a rifle riser (a mount piece under the part) optic.reliefOnRiser instead, when given.
- optic.reliefOnRiser: Optional: the eye relief when the part sits on a riser (a pistol dot lifted to a rifle sight line), metres (0.03 to 0.4). Eye relief belongs to the mount, not the file: a pistol cut and a riser put the eye at different distances.
- optic.reflex: A reflex or holographic sight's window { f, y, w, h, round?, kind: dot|dotG|dotP|cdot|holo }, centre [forward, up] and size, in the part's frame (becomes info.reflex shifted to the gun). The game draws a collimated reticle behind it; it lies inside the model's bounds and y equals sy.
- optic.pip: A scope's ocular lens { f, y, r } in the part's frame (becomes info.pip): a magnified sight needs it and the part's zoom/reticle/px (set.scoped). y equals sy.
- optic.magnifier: true when a magnifier goes behind it (a reflex sight with a window); the gun gets the anchor mount_magnifier [fSight, sy, 0].
- optic.height: low, mid or high: how tall the sight stands, for ordering and tests.
- part: The catalogue entry (js/parts.ts takes it from a generated block, `check:models -- --write` rewrites it): mount (the rail interface: op:pic, a Picatinny top rail), brand (a key of the brands), name, price, tier, zoom (the ADS FOV multiplier), st (stat deltas), and for a magnified sight scoped: true with reticle (cross|chevron|lpvo|ring), px (magnification) and optionally levels. The part is fittable and buyable on every gun that has that mount, with no per-gun data.
- The same part is the same file on every gun: the model never depends on a gun. Nothing is stretched.
- Bounds, origin and window are checked on the file (tools/authored_parts.mjs): a vertex below the rail top, a window outside the model, a window not on the sight line and an unknown material are errors that name the mesh and the number.
- MOUNTS. op:pic: the origin is the top of the rail at the optic's mount point. op:pso (the pistol optic cut): the origin is the top of the slide at the optic's mount point, the plane the foot rests on, so the same file also sits on a riser (the pistol optic riser, or a riser dot on a rifle: the riser is the gun's mount piece `optic@mount`, the part sits on its top). A pistol takes the part at 0.32 x the factory slide length from the slide's rear on the factory slide's top, whatever slide is fitted.
- REPLACE-ONLY (`"replaces": ["<entry name>", ...]` instead of `"part"`): the file becomes the model of existing catalogue entries (matched by their exact name in js/parts.ts); ids, stats, prices, tiers, mounts, build codes and what they open stay as they are, the generated block adds no part. An entry that uses a riser keeps its riser as the mount piece. Entries that are not listed (another pistol dot that shares the old model) keep the old model.
- On a gun with TASK-3 mount pieces the rail under the part is `optic@mount`; the part's own meshes are the `optic` pack and are shared across guns by content.
- FURNITURE REPLACES BY NAME OR BY MATCH. A "replaces" item is an entry name, or a match { "mount"?: "<mount>", "model": { ... } } that takes every entry of the slot (on that mount) whose catalogue model has those values (nested objects compared key by key, null meaning absent, numbers to 1e-6; keys not given are free: a finish). (For a standard-issue part with no name of its own that is the same product as a named one.) A match that takes nothing, or a name not in the catalogue, fails js/parts.ts. A handguard's replaced entries must have a length within 1.5 mm of part.len (the catalogue's length decides the fit, hgRoom; the model is drawn at its own).
- FURNITURE FINISH. The meshes in the slot's finish material (stock and grip: polymer; handguard: black; a muzzle device has none) take the catalogue entry's finish as the procedural part would have (a stock's sm or the gun's furniture, a grip's gm, a handguard's hg.m or the receiver's colour); the other meshes keep their own materials.
- FURNITURE IN THE GUN. The recipe seats the part's origin at the gun's mount_<slot> (an authored gun's anchor; on a recipe gun the point its procedural part hangs from), with no rotation and no scaling, and the part's anchors replace what the procedural part gave info: muzzles (the device's front), grip, support (when no foregrip or other hold decides it). On an authored gun the factory part is still the model's own meshes while fitted.
- furniture stock: frame "stock-mount": the ORIGIN on the buffer tube's axis at the receiver's rear (the gun's mount_stock), the stock reaching back from it (nothing more than 10 mm ahead of the origin, at least 50 mm behind); the buffer tube itself is the gun's mount piece (the recipe draws it), not the model. anchors butt (the butt plate's centre) and cheek (the top of the comb under the eye), both behind the origin. part { mount (the stock interface: tube), position? (how far it is drawn out, free text) }. Finish material: polymer.
- furniture grip: frame "grip-mount": the ORIGIN at the grip's front top, where it meets the receiver's underside (the gun's mount_grip); the grip hangs below and behind it (up to 30 mm above the origin, inside the receiver; at least 50 mm below; nothing more than 20 mm ahead). anchor grip (where the palm sits). part { mount (the grip interface: ar) }. Finish material: polymer.
- furniture muzzle: frame "muzzle-mount": the ORIGIN on the bore axis at the barrel's end, where the thread ends (the gun's mount_muzzle); the device reaches forward from it (at most 10 mm back over the thread, at least 10 mm forward), centred on the bore. anchor muzzles: [[forward, up, right], ...] where the bullet leaves it, at the device's front (within 5 mm). part { thread (the thread family, e.g. r556), kind (the device kind, e.g. flash) }. No finish.
- furniture handguard: frame "handguard-mount": the ORIGIN on the bore axis at the handguard's rear, against the receiver's front face (the gun's mount_handguard); the handguard runs forward from 0 to part.len (both ends within 3 mm), centred on the bore. anchor support (where the support hand holds it, between its ends). part { t (the handguard kind: rail), len (metres), rails? { top, bottom, left, right: [from, to] forward of the origin } }. Finish material: black.
- magnifier what: A FLIP MAGNIFIER behind a reflex sight (models/parts/magnifier/<id>/), replace-only: model.json { "source": "authored", "kind": "part", "slot": "magnifier", "frame": "magnifier-mount", "anchors": { pip, hinge, foot, foot_end }, "magnifier": { px, len, relief, pip: { f, r }, flip: { part, axis, out_deg } }, "replaces": [entry names] }. It replaces the procedural magnifier (tools/models/recipes.ts S.magnifier) for the entries it names; a magnifier with no authored model keeps the procedural one.
- magnifier frame: frame "magnifier-mount": the ORIGIN is the red dot's eye point, the gun's mount_magnifier = [the sight's fSight, its sy, 0]: the sight line runs along forward at up 0, right 0. The tube runs back from forward -0.025 (a 25 mm gap behind the sight) to -0.025 - len; the rail clamp is at the tube's FRONT, forward -0.059 to -0.025, its foot 34 mm under the sight line (a red dot's height over its rail), so it needs only 34 mm of rail behind the sight. The recipe seats the origin at mount_magnifier with no rotation and no scaling.
- magnifier nodes: The root (named after the part, extras.anchors_json = model.json's anchors) holds the fixed meshes (the clamp: "magnifier_<n>") and ONE node part_magn (extras.part "magn"), the swinging tube: its translation is on the hinge's axis (anchors.hinge), its meshes ("magnifier_<n>") under it. Nothing else is a node.
- magnifier anchors: pip: the tube's rear lens (the picture-in-picture disc's centre; at forward magnifier.pip.f, up 0, right 0); hinge: a point on the hinge's axis, the part_magn node's place; foot and foot_end: the clamp's foot, its rear and front ends on the rail top (tools/check_magnifier_rails.mjs reads the span).
- magnifier magnifier: px: the power (the catalogue's set.magnifier decides the zoom; the bake checks they agree); len: the tube's length, metres (the catalogue entry's model.magnifier.len to 1.5 mm); relief: the eye relief behind the tube's rear while aiming through it, metres (info.relief; info.fSight is the tube's rear, origin + pip.f); pip { f, r }: the rear lens, forward of the origin (-0.025 - len, within 1 mm) and its radius (info.pip, hung on part_magn so it swings with the tube); flip { part: "part_magn", axis: "y" (the tube's own forward axis, Blender Y: the only one), out_deg: the angle it swings to when flipped out, degrees as the game turns the node: about the axis pointing BACK at the eye, negative clockwise as the shooter sees it (S.magnifier's about -160, out to the right for a hinge on the right) } (info.magnOut, radians).
- magnifier rules: Materials: black, steel, rubber, glass (catalogue names). The clamp is centred over the rail, the tube on the sight line; swung out by out_deg about the hinge, the tube clears the sight line to the side of the hinge (checked). No glass may be on the eye side of the pip disc (checkPipClear, as an optic's).
- example: `{"name":"falcon","extras":{},"child":{"name":"optic_1","extras":{"slot":"optic"},"material":"black"},"model_json":{"source":"authored","kind":"part","slot":"optic","frame":"rail-top","optic":{"sy":0.0285,"fSight":-0.026,"relief":0.09,"reflex":{"f":0.0135,"y":0.0285,"w":0.026,"h":0.026,"kind":"dot"},"magnifier":true,"height":"low"}}}`

**Magazine check** (`part_mag.extras.check`, meshes' `extras.chk`):

- what: The magazine check (hold R: the magazine is pulled out and looked at) shows what is in it on the magazine's own body: the top round, witness holes stamped with a count, or the rounds themselves through a clear body. The model says which of its meshes are those (js/gunrig.ts reads it; a gun without it simply shows nothing).
- part: `part_mag` has extras.check = { w, spine? }: w the magazine's width in metres (the width of a hole's stamped count); spine (a clear magazine that has a follower and spring) the centreline samples [[t, f, y, tilt], ...] from t = 0 (the top round) down to the floor plate (the last sample's t): f and y the centre in metres in the gun's frame (forward, up), tilt the radians of a mesh rotation about x on the face there (the turn a round or hole has). t is the depth the rounds are read at.
- meshes: Meshes under `part_mag` carry extras.chk = { role, i, t?, side? }: role "top" (the round on top: i 0 its case, i 1 its tip; the game colours them for the load), "hole" (a witness hole, i = its order from the top, t = 0..1 how far down the stack it reads, side = 1: holes go down the back face of the magazine only (toward the shooter, what you see checking it; the front has none), each its own mesh, and the game stamps the count beside each. The rotation of the mesh node is the tilt of the face there: on a curved magazine each hole, and the count beside it, follows the curve; a round of a clear magazine leans with it the same way), "round" (the i-th round drawn through a clear magazine, t = how far down), "tip" (the bullet tip of round i), "follower" (the follower plate: i 0, t = the depth it is drawn at) and "spring" (coil i of the spring: t = the depth it is drawn at, u = 0..1 how far from the follower to the floor plate it sits). The game slides the follower to just under the lowest round that is in (under the top round when none is below it) and spreads the coils evenly from it to the floor plate along check.spine, each moved by the spine's difference between the depth it is drawn at and its new one (position and tilt about x): the spring is extended when the magazine is empty, squeezed on the floor plate when full, and a curved magazine's follows the curve. They are drawn at any one pose (their node transforms are the rest pose); only clear magazines have them (an opaque body would hide them) and a model without them, such as a drum, simply shows none. Every mesh keeps a slot and a catalogue material like any other; the game replaces their materials as the rounds change. A gun with a magazine check has both top meshes.
- example: `{"name":"part_mag","extras":{"part":"mag","check":{"w":0.024}},"child":{"name":"mag_91","extras":{"slot":"mag","chk":{"role":"hole","i":0,"t":0.1567,"side":1}}}}`

**Multi-barrel guns and reload sequences** (`info.barrels`, `info.hinge`):

- what: MULTI-BARREL GUNS AND RELOAD SEQUENCES (any gun; the first is the Tempest). A gun with several barrels says so in info.barrels = { n, rounds: { <type>: { rounds_each, effective_mm: [...] }, ... }, default } (info.muzzles has n entries, barrel i at muzzles[i]); the game keeps rounds_each rounds per barrel (of the round type loaded in the block: a longer round, fewer of them in the same stack) and fires from the barrels the fire mode asks for. info.barrelGroups names sets of barrels by index (top, bottom, all).
- speed: rounds.<type>.effective_mm[k] is the effective barrel length of the (k+1)-th round of that type fired from a fresh barrel: the more of a barrel's stack is gone, the longer the bore the next round runs down. The game sets the shot's muzzle velocity from it (js/data.ts G.shotDef: damage, which goes with the energy, and range run from a fraction, def.barrels.full = 0.8, of the full figures at the shortest length to 1.0 at the longest). The report is the synth's for that barrel length, with its pressure and charge scaled by it (js/parts.ts soundSpec) and the shot's gain by the square of the same factor, so a barrel sounds fuller and louder as it empties. A shot from several barrels plays one report per barrel, stacking.
- display: A display surface named display_ammo (the contract's Display surfaces) is painted with the rounds left: one row per barrel in info.muzzles order, one pip per round (lit while the round remains); u runs left to right and v away from the shooter's end (js/viewmodel.ts).
- dial: info.modeDial = { at, axis, modes, stepDeg }: the fire-mode dial, turned about its axis by stepDeg for each position of the selected mode in modes (js/player.ts). If the model has a `part_dial` node (PARTS key dial) holding the dial's meshes, that node turns about its pivot; without one the game puts a marker on the dial's face at `at` and turns that (the model's own pointer then stays where it was drawn).
- hinge: info.hinge (root extras.hinge_json) = { sequence: [...] }: the steps of a reload that takes the gun apart, in order, each moving ONE part_ node by rotate_deg about axis x, y or z (three.js rotation about the node's own pivot) or by move [forward, up, right] metres in the frame of the part_ node named by frame (default: its parent's). Parts may nest (part_brk > part_pump > part_mag > part_carry): a pack stores each node under its parent (extras.parent) and the assembled gun nests them, so a step moves everything inside the node. The viewmodel plays the steps one after another over the first half of the reload (the old block comes out), then back (the new one goes in): js/vmanim.ts hingeClip. How each step feels is the step's own optional data: share (its part of the time, relative: the reload's length, def.reload, is shared out over the steps, the hand's moves between them and a moment with the block clear), ease and back.ease (smooth, linear, in, out, spring, detent, heavy, magnet: smooth (eased in and out), linear, in (speeding up), out (slowing down), spring (released: a sharp start, past the end by over, settled back; the gun kicks), detent (a firm pull: it creeps, holds at a detent, then gives and drops onto its stop; the hand leads, the gun dips with the effort), heavy (a weight lifted: slow, the gun sagging under it and recovering), magnet (drawn in: speeding up all the way, then a soft, damped stop with no bounce). The gun's own kick, dip and sag go with the ease), over (a spring's overshoot), and hand { part, at } (the support hand on that part_ node at that point of it, following it; the right hand stays on the grip). A step without them is smooth, of equal share, the hand where it was. The sequence is data, not a gun: any model with a hinge_json gets the animation. Part keys used: lever, carry, pump, brk and mag keep their ordinary names but are driven only by the sequence on a gun that has one.
- example: `{"barrels":{"n":6,"rounds":{"standard":{"rounds_each":7,"effective_mm":[244,288,332,376,420,464,508]},"rifle":{"rounds_each":4,"effective_mm":[310,375,440,508]}},"default":"standard"},"barrelGroups":{"top":[0,1,2],"bottom":[3,4,5],"all":[0,1,2,3,4,5]},"hinge":{"sequence":[{"part":"part_lever","axis":"x","rotate_deg":40,"ease":"out","hand":{"part":"part_lever","at":[0.02,-0.02,-0.05]}},{"part":"part_pump","move":[0.09,0,0],"ease":"spring","over":0.06,"back":{"ease":"magnet"}},{"part":"part_mag","move":[0,0.1,0],"frame":"part_brk","share":1.5,"hand":{"part":"part_carry","at":[0.056,0.004,0]}}]}}`

**Bipods** (`part_bipod`, its legs' `extras.leg`):

- what: A BIPOD is one node, `part_bipod` (PARTS key bipod, listed in info.anim.bipod), whose children are its LEGS: each leg is a `group_<n>` node with extras.leg = { deploy: [rx, ry, rz] } holding that leg's meshes. A leg's pivot (its node origin) is its hinge. The model is drawn FOLDED: every leg at rotation 0. part_bipod's own origin is only a reference point (the first hinge) and nothing turns it. The legs' meshes are slot fg when the bipod is a foregrip option (the Kodiak) or slot base when it is part of the gun (a machine gun's, a sniper rifle's); one gun may have both, in the one part_bipod node.
- pose: extras.leg.deploy is the leg's rotation when the bipod is DOWN: three numbers, radians, an XYZ Euler rotation about the leg's pivot in the gun's frame (x right, y up, z back), the legs pointing at the ground and splayed a little. A leg folded back along the gun (its foot behind the hinge) turns by +PI/2 about x, one folded forward by -PI/2. Folded is rotation 0 (how the meshes are drawn): the folded and the deployed pose are both data of the model.
- drive: The game drives every leg with the same rule: rotation = deploy * smoothstep(k), k from 0 (folded) to 1 (down) over a quarter of a second, set by the player's stance and what is in front of the gun (js/player.ts bipodStep for the first person, a remote player's state in js/rig.ts for the third) and posed by G.GunRig.bipodPose(part_bipod node, k). The first-person model poses the live part_bipod node; the third-person (merged) model pulls each leg out on its own so it can turn.
- packs: In a pack the part_bipod node holds no mesh itself (the base pack owns it); each leg is a group_<slot>_<n> node with extras.parent = "part_bipod" and extras.leg, directly under the pack root like every node.
- example: `{"name":"part_bipod","child":{"name":"group_7","extras":{"leg":{"deploy":[1.5708,0.2,0]}}}}`

**Per-part pieces** (assets/models/parts: one file per part, assembled by rules):

- layout: assets/models/parts/<platform>/index.json and assets/models/parts/<platform>/<tag>/<file>.glb: one file per PIECE (a part's shape on that platform), never per combination of parts; a piece that is the same shape on several platforms (or at several places) is stored once, in assets/models/parts/_shared/<tag>/<file>.glb (see "shared"). The bake's output and its work grow with the number of parts and platforms: each part fitted once from each base build (the platform's default and loaded builds), nothing enumerated over combinations.
- pack: A piece file is a glTF binary holding ONE tag's meshes (every mesh extras.slot = the tag's mesh slot) as ONE part draws them (its provider: "tags"), in the gun's frame as in the build it was taken from (or, shared, from its bounding box's corner); `at` in the index moves it to where it sits when no other part offsets it. A tag is a mesh slot, or `<slot>@<anchor>` for a piece placed by another part (optic@barrel: an iron sight's front post, on the barrel).
- root: The file's one root node is named `<platform>.<tag>.<n>` and has extras.pack = { platform, tag, key: { <slot>: <partId> } (the provider; {} for the platform's own or a shared file) }. No transform, no info. Its children are meshes (`<slot>_<n>`), part_ nodes and group_ nodes, all flat directly under it.
- nodes: part_ and group_ nodes sit directly under the root with their position = the pivot in the GUN'S frame (not relative to a parent); extras.parent names the node they nest under in the assembled gun (absent: the gun's root). extras.owner = false means the pivot belongs to another piece (e.g. an optic's meshes inside the slide's part_slide: the slide's piece owns the node, the optic's repeats it so the meshes know where it is); the assembler takes the node from its owner (default: owner) and re-expresses every other piece's meshes against it. Group nodes are named `group_<slot>_<n>` so they are unique across pieces.
- index: The platform index.json (version 3) is { version, platform, src, slots, tags, anchors, values, info }: tags: { <tag>: { from: [<build slot>...], pieces: { "<slot>=<partId>" | "" [+ "#<label>"]: { file, at: [f,u,r], nodes?, rear?, len?, len0?, tris, bytes } }, vary?, cond?, stretch?, show?, cap?, pair? } }; anchors: { "<slot>=<partId>": { mount_<tag>: [f,u,r], "mount_<tag>?<slot>": [f,u,r], len_<tag>, cap_<tag>, pair_<tag> } }; values: { "<slot>=<partId>" | "": { <spec key>: <JSON text> } }; info: { <leaf>: { from, skip?, own: { <provider>: value }, vary?, off?: { <slot>: { x: { "<slot>=<partId>": n }, y?: { <slot>: { ... } } } }, max?: { by, v } } }. A build slot is the gunsmith's slot id (barrel, handguard, optic, riserdot, tac...); "<slot>=" (nothing after the =) is the slot left empty, which may give offsets too. docs/gun-parts-index.schema.json is the JSON Schema.
- tags: WHO DRAWS A TAG. Its provider is the first slot of `from` that is filled (a dot on a riser before the riser: riserdot before optic); its part's piece is pieces["<slot>=<partId>"]; with `from` empty, or none of its slots filled, the provider is "" (the platform's own piece). A provider with no piece draws nothing of the tag: the tag is absent (a red dot has no front sight post).
- variants: VARIANTS (vary: { by, key }). Where a part draws a few shapes, the piece key gets "#<label>", the label being the deciding part's spec value: values["<by>=<partId>"][key], else values[""][key], else "null"; "none" when the slot `by` is empty. The variants found are listed in docs/models.md ("Per-part bake"): the railmount's collar by the bore it clamps round, the Thor's irons by its barrel's sight rise.
- offsets: PLACEMENT. The piece moves by `at` plus the SUM over every build slot s other than the provider's own of anchors["<s>=<part in s>"].mount_<tag> ([forward, up, right] metres; an empty slot is "<s>="); plus, for each slot c of `cond` that is filled, the sum of anchors[...]["mount_<tag>?<c>"] (an offset a part gives only while another slot is filled: a barrel moves the sight forward only with a magnifier behind it). A CAP (cap: { axis, by, of, op }) replaces, on one axis, the sum over the `of` slots by min (op "min") or max of it and anchors["<by>=<part>"].cap_<tag> (when that part has one). A PAIR (pair: { axis, h, by, op }) makes the offset on one axis min (or max) of anchors["<h>=..."].pair_<tag> and anchors["<by>=..."].pair_<tag> (either alone when the other has none): a railmount at its handguard's end, no further than the barrel allows.
- stretch: STRETCH (stretch: true; the piece has rear, len, len0). The piece is scaled along the bore about its rear: every point's forward position in the file f becomes rear + (f - rear) * L / len, then the piece is moved as any other; L = len0 plus the sum over the slots but the provider's of anchors[...]["len_<tag>"]. Exact for the boxes it is used on (a bead sight's rib, as long as the barrel runs: its normals are along the axes). A negative L (a barrel that ends behind where the rib starts) reverses it.
- show: THRESHOLD (show: { a: [slot, key], b: [slot, key], gt }). The tag shows only while value(a) - value(b) > gt, value(s, key) being values["<s>=<part>"][key] else values[""][key] (parsed JSON): the G36's barrel sleeve, only where the barrel is longer than its handguard by more than the sleeve. The bake builds every pair of parts whose difference falls between the last absent and the first present one, so gt is exact for every pair the catalogue can make.
- info: INFO. Each leaf of `info` (a/b/0 paths: infoLeaves) is PROVIDED: by the first filled slot of its `from` whose part is not in `skip`, else the platform (""); with `vary`, "#<label>" as a tag's. Its value is own[provider] ({ "del": 1 }: the leaf is absent), plus, when off[<provider's slot>] is given, the sum over the other slots of off[...].x["<slot>=<part>"] and, for each condition slot c filled, of off[...].y[c][...]: a part's value moves with the part (the sight line with the optic's riser and a magnifier, the support hand with the handguard a foregrip is on). With `max: { by, v }` the leaf is the larger of that and v[<the part in by>] (a pistol chassis's front, ahead of a short slide's muzzle). The offsets are solved exactly from the recipe's values. Then `info.anim` from the pieces' nodes and `info.mounts` (mount_<tag>: each piece's offset) for reference.
- assembly: ASSEMBLY (G.Models.assemble(def) in js/glb.ts, synchronous: the piece files must be loaded, G.Models.ensure(def) / preloadPlatform(id) load them; G.Models.planBuild(index, build) is the pure planner, no three.js). For each tag: the provider and its piece (or none), the offsets, the stretch; the owner nodes from the pieces, every piece's meshes placed against them. G.Models.infoOf(def) gives the build's info from the index alone (no piece files), synchronously. A build the index cannot plan (a part it has no piece or value for) is assembled from what it has and the result says `approx` (the tests count that as a failure).
- shared: SHARED PIECES. A piece that is the same shape on several platforms (an optic, a magnifier, a light, a foregrip, a muzzle device) or at several places is stored once: in assets/models/parts/_shared/<tag>/<file>.glb, in its own frame (the origin at the corner of its bounding box: smallest forward, up and right), and each platform's piece entry names it with the `at` that places it. Two pieces are one when their triangles agree to 2 micrometres after the move.
- mounts: MOUNT PIECES (optics and front sights). A sight is ONE object, the same file on every gun, built in its own frame: the origin on the TOP of the rail (the surface its foot rests on) at its mount point, centred; metres, [forward, up, right]; everything it tells the game (sy, fSight, relief, reflex, pip, mount_magnifier) is in that frame. What is specific to a gun between the gun and the sight is a MOUNT PIECE, a tag of its own: `optic@mount` (the rail section under the sight, a riser, an adapter, the fixtures of the gun's own sights, a pistol optic plate). An iron front sight is its HEAD `optic@barrel` (post, ears, hood: placed by the barrel, at the length its front sight stands) on its BASE `optic@sightbase` (the column from 4 mm over the bore up to the head); a bead `optic@barrelend` (at the barrel's end), its rib `optic@rib` (stretched) and the rib's posts `optic@ribpost<i>`; a front sight at the barrel's end of a gun's own irons `optic@barrelend` and its base `optic@endbase`. A recipe draws a piece of another part's with k.at(<anchor>).
- verify: VERIFICATION. In the bake, per platform: every rule is solved from the builds and must explain each of them exactly (each piece against every build it is in, each offset across the parts it applies to, each info leaf to 1e-9); then every one of those builds and a random sample of others (MODELS_SAMPLE a platform, 5 by default: a few hundred) is planned from the index by the game's own planner and compared with the recipe vertex for vertex (to 0.01 mm) and leaf for leaf; the bake fails otherwise. `npm run test:models` assembles the edge cases and regressions through the real files (glb, decoder, assembler) against the recipe and the golden fingerprints; `npm run test:models:full` adds the whole sweep and 10,000 random held-out builds.

A one-off colour that isn't in the catalogue is named `m_<rrggbb>` (hex colour) and is kept as exported: a standard PBR material, no bump.

**Extras keys:** root: `info`, `gun`, `anchors`; mesh: `slot`, `display`, `chk`; part: `part`, `anchors`, `owner`, `parent`, `leg`, `check`; pack: `pack`.

## Barrels, grips and box handguards (one object on every gun)

- **A shared barrel is cartridge x length x profile** (`br.<cartridge>.<inches>` is the standard profile, `.light`, `.tapered`, `.heavy` the others): ONE object on every gun that takes it. It is a tube as long as the barrel (inches x 25.4 mm + a 6 mm shank) at its profile's radius, drawn ending where that length ends on the gun: the gun gives only the place of its factory barrel's end, so the part is never scaled and the same file is on every gun (the part inside the receiver is hidden by it). `js/parts.ts` `BARREL_PROFILES`: standard 9.5 mm, light 7.0 mm, tapered 9.5 mm to 7.6 mm at the muzzle, heavy 12 mm (14 mm on the .50 BMG). A profile carries figures (weight, handling, recoil, accuracy) against the profile of the gun's own barrel (zero for that one), so a gun's own barrel keeps its exact figures and two barrels of one gun never read the same.
- **Fit.** A barrel of 0.6x to 1.6x the factory length that leaves at least 60 % of what the gun's own barrel shows (visible length = the model's own + the length's difference from the factory one); the FAL takes none ending before its gas block (17" up).
- **The FAL's own barrel** is its model's mesh (`fal.barrel`); every other FAL barrel is the shared one.
- **AR grips** are one shape in one colour (the M4's): the exceptions are the F2, the GM6 and the FAL's own grip. **Box handguards** (mount `hg:box`) likewise: the AA-12's draw in the standard colours; the FAL's own wooden handguard is its model's.

## Authored models (Blender)

A gun modelled in Blender is **baked straight from its .glb with no recipe**. The source is two files:

- `models/<id>/<id>.glb`: the model (below);
- `models/<id>/model.json`: `{ "source": "authored", "sights": { "builtin": [...], "rail": [...] } }`. It marks the .glb as the authority for the gun (a gun without it is built by its recipe in `tools/models/recipes.ts`), and says which optic kinds mean the gun's own iron sights (`builtin`: irons, notch, bead, riser...) and which of those still put a rail piece on the receiver (`rail`: a riser).

The format and its rules are the contract's **Authored sources** section (generated above from `js/glb.ts`: root `extras.info`, `extras.anchors`, the required `mount_<slot>` anchors with what each means). In short:

- **The model holds the factory gun**: the base (receiver: every slot `base` mesh outside a `part_` node) and the factory parts as meshes by slot (`stock`, `grip`, `handguard`, `barrel`, `muzzle`, `optic` = the gun's own irons), one catalogue material per mesh; the magazine is `part_mag` (slot `mag`), the charging handle `part_handle`, any moving part a `part_<key>` node with its pivot at the node origin. Which slots must be modelled is the platform's default build (js/parts.ts); a missing one is an error naming it. Part ids are the platform's: the model does not repeat them.
- **Info anchors** (`sy`, `fSight`, `relief`, `muzzles`, `grip`, `support`, `magAt`, `handle`, `port`, `chamberAt`...): the contract's `info`, in root `extras.info` (or the text `info_json`: Blender stores only flat properties).
- **Mount anchors** (root `extras.anchors` / `anchors_json`, [forward, up, right] metres in the gun's frame): `mount_optic` + `mount_optic_end` (the optic rail's span on the receiver, at the receiver's top), `mount_handguard` + `mount_handguard_end` (where a handguard starts and the furthest forward one reaches), `mount_barrel` (where the factory barrel starts), `mount_muzzle` (the factory barrel's end, where a muzzle device screws on), `mount_stock`, `mount_grip`, `mount_mag`. Extra `mount_<slot>` anchors (a side rail: `mount_tac`) are allowed. The barrel is the model's own while the platform's own barrel is fitted (slot `barrel` holds just that barrel); the gas block, gas tube, bayonet collar and any other fitting that stays when another barrel is fitted are slot `base`.
- **Every part the gun accepts that is not the model's own is seated from those anchors**, at its own designed size and never stretched: the optic rail piece over the optic span, a handguard from `mount_handguard`, a stock centred on `mount_stock`, a grip hung from `mount_grip`, another magazine in the well at `mount_mag` (the platform's `magFit` fits it), a muzzle device and the front sight on the barrel's end, the optics (the shared optics, riser dots, magnifiers) on the rail by the platform's spec (`optF`). Another barrel is the shared barrel of its length and profile (see "Barrels" below), ending where that length ends from `mount_muzzle`: nothing in the model is resized.
- **A receiver with no rail** (the MP5's): the model holds its own **optic mount**, the adapter a rail sight goes on, as meshes of slot `optic` with `extras.mount = true`, and its rail as `mount_optic_rail` .. `mount_optic_rail_end` (the rail's top height). With a real optic (or a riser) fitted the recipe draws those meshes as the optic's mount piece (`optic@mount`) instead of the generic rail piece, and the sight stands on that rail top at `optF` (so `info.sy` comes out of the mount's height); with the irons alone nothing of it is drawn. It is not part of the irons (`checkIrons` leaves it out). The contract's `opticMount` entry has the rules; `mount_optic` / `mount_optic_end` stay the receiver's top under it.
- **Fit is data, not geometry**: which handguards, barrels and optics the gun takes is decided by `js/parts.ts` (`fitsSlot`, `hgRoom`/`hgMax`), not by the model. A handguard longer than `mount_handguard_end - mount_handguard - 3 mm` is not offered (spec `hgMax`), nothing is clamped. The platform's spec in `js/parts.ts` must say `rcv: 'authored', authored: '<id>'` and agree with the anchors (`L` = `mount_handguard`, `hgMax`, `mag` = `mount_mag`): the baker fails otherwise, naming the disagreement.

**Checking.** `npm run check:models -- models/<id>/<id>.glb` validates a source (the contract's authored rules, then the platform's spec); `test:models` does it for every authored gun, with negative tests for each rule (`tools/check_models.test.mjs`) and `tools/check_authored_golden.mjs` (the golden fingerprints, `tests/model-golden-<id>.json`: the sweep and edge builds, `--update` rewrites them).

**Model checks** (`tools/authored_checks.mjs`, run by `checkAuthored` after the contract and spec checks pass, so by `check:models`, `test:models` and the bake; tests in `tools/check_authored_checks.test.mjs`, a gun made of boxes that passes each rule and a copy broken for each). They measure the model's own triangles, in the gun's frame, and each message names the gun, the mesh and the numbers. Errors unless marked:

- **a. Irons** (when `sights.builtin` has an iron kind, `irons`, `notch`, `bead` or `qbzirons`, and the sights are not `meshless`). The eye is `[fSight - relief, sy, 0]` and the sight line runs forward from it, level, on the bore plane. The irons are found by geometry, not by slot or name (a front sight on the barrel slot or the base counts the same as slot `optic` meshes). The **front post** is the furthest-forward place where a ray straight down at right = 0 meets a surface within -1.5 to +0.6 mm of `sy`: its tip is at `sy`. Its width 1 mm under the tip must be at most 1.2 degrees from the eye. The line from the eye to just under the tip must reach the post, and a cone 0.6 degrees round the tip (beside and over it) must be clear from behind the rear sight to 25 mm short of the post. The **rear sight** is what stops rays fanned out from the line (16 directions, each to the first angle that is stopped) within the nearer 70 % of the sight radius (80 % on a pistol: a rear sight ahead of an optic cut, the 2011's, stands about three quarters of the way to the post at the pistols' 0.36 m relief): closed over the top it is an **aperture**, and its radius (the mean over the directions, as a ring is modelled as a polygon) must be at least 2.35 degrees (about 2.4: the Mk18's 3.2 mm at 76 mm is 2.41), with `relief` 0.06-0.09 m on a long gun (a warning outside it); open on top it is a **notch**, at least 1.5 times as wide as the post as seen from the eye (light either side). Nothing in the rear part (a bead, a front sight only) checks just the post and the line.
- **b. Magazine check** (a box magazine; a drum, a belt, a gun with `info.barrels` need none): `part_mag` `extras.check.w`; `chk` `{ role: "top" }` meshes `i: 0` and `i: 1`; and witness holes (`role "hole"`: for each `i` exactly one mesh, on side 1, the back face; none on the front) or clear-body rounds (`role "round"`).
- **c. Top round**: the crown (the top of the `top` meshes) at most 3 mm under the magazine body's top, and not under the feed lips' top. Under `part_mag`, the lips are the meshes without `chk` that are thin across (under 35 % of the magazine's width) in its top 15 mm; other rounds are the ones no wider or taller than the top round and not above it; the body is the rest.
- **d. Handguard room** (when the catalogue can replace the factory handguard: the handguard slot's mount offers shared parts, not only the gun's own, as the Tempest's): the slot `handguard` meshes end at least 15 mm behind `mount_muzzle` (js/parts.ts `hgRoom` keeps that for a muzzle device's thread; not when the muzzle slot takes only the gun's own devices), and are no longer than the platform's `hgMax`; the default build's handguard part (`model.hg.len`) is no longer than `hgMax` either.
- **e. Magazine well**: the well is what encloses the magazine's axis (the vertical at `magAt`'s forward, right 0): at each mm of height, a receiver mesh (slot `base`, outside any `part_` node) that level rays from the axis forward, back and to both sides each cross an even, non-zero number of times is a wall there (a hollow shell round the axis; a solid the axis is inside, a block filling part of the well, is not). Every vertex of the magazine, and points 1 mm apart along every edge, at a height with walls must not be past a wall along the ray from the axis by more than 0.5 mm. A model with no hollow well round `magAt` (a receiver modelled as one solid with the magazine pushed into it: the FAL, the pistols) is not measured, with a warning.
- **f. Furniture as parts** (a warning): each factory `stock`, `grip`, `handguard` and `muzzle` the model holds is a catalogue part (the default build's); one whose mount fits other guns should have a `models/parts/<slot>/<id>/model.json` whose `replaces` names it, so it does not keep the recipe's procedural look wherever else it is fitted.

**Waivers** (`tools/authored_waivers.json`: `{ "<gun>": { "<rule letter>": "why, and what fixes it" } }`). The models that already failed a rule when the rules came in (2026-11-05: fal a, b and d, maxim9 b, welrod a and b) are listed there, so the bake and CI do not stop on them: a waived gun's failures of THAT rule print as warnings, `WAIVED (tools/authored_waivers.json <gun>.<rule>: <note>): <the error>`, so they stay in sight. Any other rule on those guns, and every gun not listed, is still an error; a letter that is not a rule (a to e) is an error; and a waiver whose rule now passes is a warning, "no longer needed: remove it". Fix the model, then delete its entry. A new gun is never waived.

**Baking.** `tools/bake_authored.mjs` is the baker's authored side: it finds the sources (`models/*/model.json`), checks each (a missing anchor or slot fails the bake with its name), reads the .glb into `G.Authored` (geometry in the gun's frame, the anchors as the seat frame, the sights rules, the info) and `tools/model_env.mjs` loads it next to the game. The generic seating (`rcv: 'authored'` in `rifle()`, `tools/models/recipes.ts`: nothing in it names a gun) builds the whole gun from it, and then the one pipeline every platform goes through learns its pieces (one part each), offsets and info rules, writes the platform index, and shares the pieces that are the same shape as other guns' (an optic is one file wherever it sits). A change to the .glb or `model.json` marks the bake stale. `npm run bake:models -- --parts fal`.

**The FAL** (`models/fal/`) is the first: `build_fal.py` builds the gun in Blender from `trace.json` (outlines and column profiles traced off a side-on photo, source and licence inside), writes the anchors above, saves `fal.blend` and exports `fal.glb`. Run it in Blender (`exec(open(r'<repo>/models/fal/build_fal.py').read(), {'FAL_DIR': r'<repo>/models/fal'})`, or `blender -b -P models/fal/build_fal.py`), then `npm run check:models -- models/fal/fal.glb` and `npm run bake:models -- --parts fal`. In Blender: X = right, Y = forward, Z = up, metres; objects carry custom properties that become node extras: `slot` on meshes, `part` on `part_<key>` empties, `gun`, `info_json`, `anchors_json` on the root empty named after the gun; material names are the catalogue's. The FAL has no recipe: `rcv 'fal'` and `tools/models/authored.ts`'s generated data and `authored_pack.mjs` are gone; `tests/model-golden-fal.json` holds its fingerprints.

**The MP5 and MP5SD** (`models/mp5/`, `models/mp5sd/`, issue #30) are built by one shared script, `models/mp5_kit.py` (each gun's `build_<id>.py` sets `CFG = {'sd': ...}` and runs it, as the AR guns run `ar_kit.py`): the stamped receiver, the SEF housing with its well, the HK grip, the A2 stock (lofted), the drum sight and the curved magazine are the same on both; the MP5's front is its cocking tube, slim handguard, front sight and three-lug end (slot muzzle), the MP5SD's is all slot barrel (the ribbed handguard round the can, the front sight, the can). The magazine is drawn on the recipe's own curved centreline (`MAG_FAMS.mp5` in js/parts.ts has the same len, d, c and w), so the shared 15-, 40-round and translucent magazines match it. The MP5SD's two other barrels are variants beside it (`barrel_long.glb`, `barrel_open.glb`, parts `mp5sd.br.long` / `mp5sd.br.open` with `model.avBarrel`): on a rifle a variant barrel (`o.avBarrel`) is drawn whole and its `info.muzzles` is where the bullet leaves (rifle() in tools/models/recipes.ts), as on the authored pistols. The MP5SD has no handguard slot: its `mount_handguard_end` is 3 mm ahead of `mount_handguard` (hgMax 0). The receiver has no rail: both carry their optic mount (`claw_mount()`, the B&T low-profile pattern: 138 mm long, 40 mm across the clamps, the rail top 17.5 mm over the receiver's top), a deck with the Picatinny rail along it and a clamp block at each end whose claws hook into the receiver's four recesses a side, the left jaws closed by throw levers; it is drawn only under a rail sight (the drum and post come off with one, as before), the sight at `optF` 0.12 on its rail (95.2 to 233.2 mm), or at `optFMag` 0.2 with a magnifier behind it: a magnifier's foot is 34 mm long right behind the sight (S.magnifier: fSight - 59 mm .. fSight - 25 mm, whatever its tube's length), so with the sight there every reflex sight's foot and every magnifier's foot are on the rail (the tightest: 1.8 mm behind the Falcon-shaped dots, 3.2 mm in front of the holographics; any optFMag from 0.1982 to 0.2032 fits). **The rear sight** is HK's rotary diopter drum (Commons "HK MP5 noBG.png"): a drum on a cross axis with its knurled rim and four settings (the large aperture in use, a V notch across its top, two smaller apertures on its other faces), between two protective ears on a base clamped to the receiver's top, the windage screw behind; the front post stands in its hooded ring, its tip on the drum's axis (`info.sy`). **The cocking lever** (`part_handle`, `info.handle.lock`) is the HK slap handle: a lever on the left of the cocking tube at 10 o'clock, folded forward along it, riding in a slot in the tube with the notch at its rear; its node's origin is on the tube's axis, so turning the part about it (`lock` radians, up) is the turn up into the notch. It does not reciprocate: it stays put while the gun fires. Every reload of a gun whose handle has a `lock` is the slap reload (`slapClip` in js/vmanim.ts, `slapSounds` in js/player.ts, the same for the third-person rig in js/rig.ts): the left hand draws the handle back, turns it up into the notch (the bolt held open), the magazine is changed, then the hand slaps the handle down out of the notch and the bolt runs home, chambering a round (a round already chambered stays in w.chamber: the game has nowhere to put an ejected live round). The MP5's other handguards are authored parts for it alone (`models/parts/handguard/mp5_slim`, `mp5_trirail`, built by `models/mp5_parts.py`; `"gun": "mp5"` in model.json, so the shared catalogue entry they replace keeps its own look on other guns): the slim forend in the finish the entry gives it (the FDE one) and the clamp-on tri-rail, the Northmark "railed front", a Picatinny rail under it and each side.

**The AK family** (`models/ak`, `models/ak74`, `models/rpk`: the KV-47 (an AKM), the AK-74M and the RPK) is built by one shared script, `models/ak_kit.py` (each `build_<id>.py` sets `CFG = {'variant': ...}`). The stamped receiver with its magazine well, the rear sight block and tangent leaf (`notch`), the gas tube, the gas block and the front sight base are the receiver's (slot base), so they stay where the factory barrel has them: no barrel shorter than the factory one is offered (`LEN_MIN_IN` in js/parts.ts). The optic mount is a railed dust cover (`extras.mount`, `mount_optic_rail` 0.038 to 0.226, its top 0.0411, 3.9 mm under the sight line), drawn under a rail sight only; the sight stands at `optF` 0.13, or `optFMag` 0.15 with a magnifier behind it, so every reflex sight's and magnifier's foot is on that rail. The RPK's bipod is its model's own `part_bipod` with its two legs (`group_` nodes with `extras.leg`): `tools/bake_authored.mjs` reads each leg's pivot and deploy rotation (`parts.bipod.legs`, the meshes' `leg`), and the recipe rebuilds the node and its legs as `bipodLeg` makes them (`authoredBipod`). The furniture as parts (`models/ak_parts.py`): the handguards `lynx_ak_204`, `valkyr_ak_208`, `northmark_ak_quad` (inside the 208 mm to the gas block), the drop-in lowers `ak_dropin_quad` and `ak_dropin_mlok` (0.158 m, rails at 3, 6 and 9 o'clock), the stocks `northmark_akm` and `kodiak_ak74m`. An authored stock on its own trunnion (part.mount other than `tube`) gets no buffer tube under it; on a handguard whose `part.rails.bottom` does not reach the recipe's foregrip seat, the foregrip is moved onto that rail, as near its back as its clamp allows.

## Authored parts (Blender): shared sights, prisms, scopes and furniture

The Blender path is not only for whole guns: a shared ATTACHMENT can be modelled the same way and joins the game as a buyable, fittable part with no recipe. The rules are the contract's **Authored parts** (generated above from `js/glb.ts`); in short:

- **Files**: `models/parts/<slot>/<id>/<id>.glb` and `model.json` beside it. The slots: `optic` (sights, prisms, scopes) and the FURNITURE slots `stock`, `grip`, `muzzle` and `handguard` (below).
- **The part's own frame** (an optic): metres, glTF axes, the ORIGIN on the top of the rail at the optic's mount point (the plane the foot rests on), centred. Nothing below y = 0: the rail section, riser or adapter under it is the gun's **mount piece** (`optic@mount`, placed at the gun's `mount_optic`), which the recipe emits; an authored optic never contains it. This is the optic/mount interface the optic builders (`S.reddot`, `S.prism`...) use too, so an authored optic is the same kind of object as a recipe's, and is one shared file on every gun (the baker finds that it only translates with the gun's rail top and optic position).
- **model.json** gives what a model cannot hold: `optic` = `{ sy, fSight, relief, reflex?, pip?, magnifier?, height }` in the part's frame (the baker shifts them by the gun's rail top and mount point into each platform's `info.sy`, `fSight`, `relief`, `reflex`, `pip` tables; a magnifier goes behind a `reflex` optic with `magnifier: true`: the gun gets `mount_magnifier`), and `part` = the catalogue entry (`mount`, `brand`, `name`, `price`, `tier`, `zoom`, `st`; for a magnified sight `scoped`, `reticle`, `px`, `levels`). The part id is derived: `op.auth.<id>`.
- **Joining the catalogue**: `npm run check:models -- --write` regenerates the block between the `authored-parts` markers in `js/parts.ts` (one entry per model.json; `test:models` fails when it differs), which `add()`s each part at the END of the list (a part's id in a code is its place in it) on its mount, so it is buyable and fittable on every gun that has that mount, with no per-gun data. The recipe sees it as `optic: 'authored'`, `apart: '<slot>/<id>'` (`sightOf` in `tools/models/recipes.ts` calls `G.AuthoredParts.place`, `tools/models/authoredparts.ts`, which places the model's meshes at the gun's rail top and optic position and records the window / lens).
- **Reticles**: a `reflex` window is drawn like any reflex sight's (a collimated reticle behind it, masked to the window); the window's centre height must equal `sy`, so the reticle is on the line of sight. A `display_<name>` mesh in the file is carried as in the contract (painted by name).
- **Building one**: in Blender, from the part's `build_<id>.py` (a shared builder per family under `models/parts/optic/`: `open_kit.py`, `tube_kit.py`, `holo_kit.py`, `pistol_kit.py`, `prism_kit.py`), which writes `<id>.glb`, `<id>.blend` and `model.json`; any glb that follows the contract works.
- **Checking**: `npm run check:models -- models/parts/optic/<id>/<id>.glb` runs the config rules, the node-tree rules and the GEOMETRY rules (`tools/authored_parts.mjs`: the lowest vertex on the rail top, not under it; centred; within the size limits; the window inside the model and on the sight line); `test:models` does it for every part, with `tools/check_authored_parts.test.mjs` (the negative tests, furniture included). The bake refuses an invalid part, names the mesh or number, and hashes the sources into its staleness check. `model_cases` adds a case for every authored part on every gun that takes it (and a magnifier behind it).
- **Mounts**: `op:pic` (a rifle's top rail) and `op:pso` (the pistol optic cut). The frame is the same for both: the origin on the plane the foot rests on (the rail top, or the TOP OF THE SLIDE at the optic's mount point). On a pistol the recipe seats the part at 0.32 x the FACTORY slide length from the slide's rear on the factory slide's top (`pistolDot` in `pistol()`; revolvers and the derringer use their own spot), whatever slide is fitted, so it is one shared `optic` pack. A riser (the pistol optic riser on a rail, or a riser dot) is the gun's mount piece `optic@mount` (`authoredOptic` in recipes.ts draws it and stands the part on its top); the same file sits on it. Eye relief belongs to the mount: `optic.relief` on a cut or a rail, `optic.reliefOnRiser` on a riser.
- **Replacing an existing entry's model** (replace-only): `"replaces": ["<entry name>", ...]` instead of `"part"`. The listed js/parts.ts entries (exact names) keep their ids, stats, prices, tiers, mounts, build codes and what they open; only their model changes to the authored file (`model.optic` becomes `authored`, `apart` the part; `model.was` keeps the old kind for ranking sights in `model_cases`). The generated block adds no part for it (it lists `AUTHORED_REPLACES`). An entry that is not listed keeps its old model (the Strix Kite pistol dot still draws the old S.minidot). The first one: **Halcyon Ember** (`models/parts/optic/ember/`, built by `build_ember.py` in Blender): "Halcyon Ember pistol dot" (op:pso). The catalogue once had a second entry, "Halcyon Ember open reflex on a riser", but js/parts.ts turned that id (op.pic.12) into the "Halcyon pistol optic riser", and the pistol dots (this one included) mount on that riser through `alsoMounts` (op:rmr): so the one file serves the pistol cut and the riser, and the riser stays the gun's mount piece.
- **The first part**: `op.auth.falcon`, the Strix Falcon open reflex (`models/parts/optic/falcon/`): 10 meshes, sight line 28.5 mm above the rail, a 26 x 26 mm window, takes a magnifier.

### Authored furniture: stocks, grips, muzzle devices, handguards

A piece of furniture is an authored part too, always REPLACE-ONLY: it becomes the model of existing catalogue entries, everywhere they are fitted (any gun), and adds none. The contract's **Authored parts** (furniture entries, above) has the rules; in short:

- **Frames**: metres, glTF axes (x right, y up, -z forward), anchors `[forward, up, right]` from the origin, which is the gun's `mount_<slot>` anchor (`model.json` `"frame": "<slot>-mount"`):

  | slot | origin (= the gun's anchor) | reaches | anchors | `part` | finish material |
  |---|---|---|---|---|---|
  | `stock` (`stock-mount`) | the buffer tube's axis at the receiver's rear (`mount_stock`) | back | `butt`, `cheek` | `mount` (tube), `position`? | polymer |
  | `grip` (`grip-mount`) | the grip's front top, where it meets the receiver (`mount_grip`) | down and back (up to 30 mm of it inside the receiver) | `grip` (the palm) | `mount` (ar) | polymer |
  | `muzzle` (`muzzle-mount`) | the bore axis at the barrel's end, where the thread ends (`mount_muzzle`) | forward (at most 10 mm back over the thread) | `muzzles` (where the bullet leaves it, at its front) | `thread`, `kind` | none |
  | `handguard` (`handguard-mount`) | the bore axis at the receiver's front face (`mount_handguard`) | forward, 0 to `part.len` | `support` | `t`, `len`, `rails`? (`[from, to]` per side) | black |

  The anchors are in `model.json` `"anchors"` and on the file's root as `extras.anchors_json` (when the file carries them they must be the same). `checkFurniture` (`tools/authored_parts.mjs`) checks the bounds against the frame: centred, the stock behind its origin, the grip under its, the muzzle device ahead of its (its `muzzles` at its front), the handguard from 0 to `len`, the anchors on the part; and no cameras or lights in the file.
- **What it replaces**: `"replaces"` lists entry names, or MATCHES `{ "mount"?: "<mount>", "model": { ... } }`: every entry of the slot (on that mount) whose catalogue model has the values given (nested key by key, `null` = absent, numbers to 1e-6; keys not given, such as a finish, are free). A match is for a standard-issue part with no name of its own that is the same product as a named one (none of the furniture so far needs one: every entry it replaces has a name). js/parts.ts applies them after every gun's parts are made (`AP_KEY`: the entry's model gains `apStock`, `apGrip`, `apMuzzle` or `apHg` = `<slot>/<id>`, nothing else, so ids, stats, prices, fits and std()'s sharing stay) and fails on a name not in the catalogue or a match that takes nothing. A handguard's entries must be within 1.5 mm of `part.len`: the catalogue length decides the fit (`hgRoom`, `hgFits`), the model is drawn at its own (the factory rail is 0.24 in the catalogue, 0.2395 in the model). `"gun": "<platform id>"` makes it one gun's model for a catalogue entry other guns share (the MP5's tri-rail for the Northmark railed front, which the Vector has too): the entry's model gains `apHgBy: { <id>: '<slot>/<id>' }` instead of the key, js/parts.ts modelSpec picks it for that gun only, and the length check is waived (the model is drawn at its own length, within the gun's `hgMax`).
- **In the gun** (`tools/models/recipes.ts`, `G.AuthoredParts.furniture` in `tools/models/authoredparts.ts`): the recipe puts the part's origin where its own part would hang from, with no rotation or scaling. On an authored gun that is the model's anchor (`mount_grip`; `mount_stock`, `mount_muzzle`, `mount_handguard` through the rig); on a recipe gun the procedural part's mount point: a stock's tube axis at the receiver's back (`stock()`: (0, -0.002); the buffer tube itself is the gun's, drawn under the model), an AR grip's front top (`gf + 0.028`, -0.036), the barrel's end for a muzzle device (`muzzleDev`), the receiver's front on the bore for a handguard (`hgF`, 0). The meshes in the slot's finish material take the entry's finish the way the procedural part would (a stock's `sm` or the gun's furniture, a grip's `gm`, a handguard's `hg.m` or the receiver's colour: the SCAR's FDE rail); the rest keep theirs. The part's anchors replace what the procedural part gave `info`: `muzzles` (the device's front), `grip` (its palm anchor; an authored gun keeps its model's), `support` (the handguard's, when no foregrip, pump or platform hold decides it). `info` has no butt or cheek of a stock (its `cheek` is a bullpup's eye), so those anchors are not used yet. On an authored gun the factory part is still the model's own meshes while it is fitted (the Mk18's furniture IS these files: `models/ar_parts.py` cuts them out of its build).
- **The furniture so far** (all from the Mk18's build, `models/ar_parts.py`: `blender -b -P models/ar_parts.py`): `stock/kestrel_cs4` (Kestrel CS-4 carbine stock: the Mk18's, AR-9's, Benelli's, MP7's... factory stock), `grip/paragon_pg23` (the Paragon PG-23 ergonomic grip: the Mk18's default grip), `grip/brightline_a2` (the standard-issue A2 grip, "Brightline A2 pistol grip (matches the furniture)": most rifles' default; on an AR grip mount it is drawn in polymer whatever the gun's furniture, so the model's own polymer finish; the rubber and OD AR grips are other products and stay procedural), `muzzle/ironvale_a2_556` (the Ironvale A2 5.56 birdcage, which is also every r556 gun's factory flash hider), `handguard/quad_rail_240` (the Mk18's factory "Brightline 9.4" quad rail handguard" and its FDE twin) and `handguard/ironvale_ir12` (the Ironvale IR-12 quad rail: also the HK416's and Mk14's factory rail).

### Authored flip magnifiers

A flip magnifier (`models/parts/magnifier/<id>/`, built by `models/parts/magnifier/magnifier_kit.py`: `blender -b -P models/parts/magnifier/magnifier_kit.py`) is an authored part too, REPLACE-ONLY: it becomes the model of the catalogue magnifiers it names (`"replaces"`), on every gun and behind every reflex sight. A magnifier with no authored model keeps the procedural one (`S.magnifier` in `tools/models/recipes.ts`). The contract's **Authored parts** (the `magnifier` entries, above) has the rules; in short:

- **Frame** `"magnifier-mount"`: Blender X right, Y forward, Z up (glTF x right, y up, -z forward), metres. The ORIGIN is the red dot's eye point, the gun's `mount_magnifier` = [the sight's fSight, its sy, 0]: the sight line runs along forward at up 0. The tube runs back from forward -0.025 to -0.025 - `len`; the rail clamp is at the tube's FRONT, -0.059 to -0.025, its foot 34 mm under the sight line (so it needs only 34 mm of rail behind the sight: the MP5's claw mount).
- **Nodes**: the root (named after the folder; `extras.anchors_json` = model.json's anchors) holds the clamp's meshes and ONE `part_magn` node (`extras.part` "magn") whose translation is on the hinge's axis (`anchors.hinge`); the tube's meshes are its children. Meshes are `magnifier_<n>`, materials `black`, `steel`, `rubber`, `glass`.
- **model.json**: `anchors` { `pip` (the rear lens, [pip.f, 0, 0]), `hinge`, `foot`, `foot_end` (the clamp's foot on the rail top: the rail check reads the span) }; `magnifier` { `px` (the power: the catalogue's `set.magnifier`), `len` (the tube: the catalogue's `model.magnifier.len` to 1.5 mm), `relief` (the eye relief behind the tube's rear: info.relief, with info.fSight the tube's rear), `pip` { `f`, `r` } (the picture-in-picture disc: info.pip, hung on part_magn), `flip` { `part`: "part_magn", `axis`: "y", `out_deg` } }; `replaces` [entry names]. `js/parts.ts` checks each named entry is a magnifier of that power and tube length and gives its model `apMagn` ("magnifier/<id>", AP_KEY), which the spec carries.
- **The flip**: the game turns part_magn about its node's z axis (three.js: the axis along the tube pointing back at the eye) to `info.magnOut` radians while the magnifier is out (`js/player.ts`; absent, -2.8, the procedural one's). An authored magnifier's `info.magnOut` is `flip.out_deg` in radians: negative is clockwise as the shooter sees it, so a tube hinged on the right swings up and over to the right (the three of them: -160). The check (`checkMagnifier`) turns the tube's axis about the hinge: halfway out it must be above the hinge (not down through the rail), and once out clear of the sight line on the hinge's side.
- **Checks** (`tools/authored_parts.mjs checkMagnifier`, `checkPipClear`; `npm run check:models -- models/parts/magnifier/<id>/<id>.glb`): part_magn at `anchors.hinge`; the tube's rear at `pip.f`, its lenses on the sight line; nothing forward of -15 mm (it stays behind the sight); the clamp's lowest vertex on `anchors.foot`'s height (not under it, not over 1.5 mm above), its foot centred and spanning foot..foot_end (3 mm); no glass on the eye side of the pip disc.
- **In the gun** (`S.magnifier(k, sight, m, anim, o.apMagn)`, `G.AuthoredParts.magnifier`): the clamp's meshes at mount_magnifier, the tube's on a hinge group at `anchors.hinge` that is `anim.magn` (baked as part_magn, the piece shared across guns like the procedural one), the pip disc on it, the feet log (tools/check_magnifier_rails.mjs) from `foot`/`foot_end`. The per-part bake learns it as any magnifier: the piece's offsets from mount_magnifier (the sight's place: optF, the MP5's optFMag, the Thor's `mount_optic?magnifier` condition), nothing of its own.
- **The three**: `magnifier/brightline_2x` (Brightline 2× micro magnifier, 60 mm), `magnifier/strix_fts3` (Strix FTS 3× flip magnifier, 75 mm), `magnifier/meridian_5x` (Meridian 5× flip magnifier, 90 mm). The edge cases fit each behind the first sight that takes one (`authored magnifier (mgn.N) behind <optic>`).

## Compression

Every pack and prop (`tools/model_emit.mjs` `compression()`, after the weld on float32 positions) is:

- **meshopt-compressed** (`EXT_meshopt_compression`, required; method `quantize`, no lossy filters): vertices reordered for it, then every buffer view through meshopt's attribute / index codecs. The page decodes it with three's own `MeshoptDecoder` (js/threeboot.ts, the same pinned three on jsDelivr), which `G.GLB.ready` waits on; the node tools with the same decoder from `node_modules`.
- **quantised** (`KHR_mesh_quantization`, required): normals to 10 bits and UVs to 12 (int16 / uint16), and **positions to int16 in each mesh's own box** (`quantizePositions`): `p = o + s * q / 32767`, `o` the box's centre and `s` its half-size, both rounded to whole micrometres. The mesh node carries `translate(o) scale(s)` in its transform (so the file is standard glTF, the right size in any viewer) and `extras.dq = [ox, oy, oz, s]` records it. One step is `s / 32767` (7.6 um for a 0.5 m mesh), the largest move half that: the model tests' largest deviation from the recipe is 0.007 mm (tolerance 0.05 mm); no golden fingerprint changed. `MODELS_POSITION_BITS=0 npm run bake:models` bakes float32 positions instead (the old, exact form).
- **dequantised as it loads** (`G.Models.dequantize`, js/glb.ts, run by `G.GLB.load` and by the tools' loader, tools/model_env.mjs): a node with `extras.dq` gets float32 positions back in its own frame and its own transform (scale / s, the translation less the rotated, scaled o, snapped to 1e-12), and `dq` is dropped. So nothing after the loader sees a scaled mesh node or integer positions: the assembler, the viewmodel merge, stickers, raycasts work on what an uncompressed file gave. GPU memory is as before (float32 positions), the quantisation saving bytes on the wire and in the store only.
- **No textures.** The packs carry no images (every material is a catalogue name or a flat `m_<rrggbb>`; bump maps and display surfaces are drawn at load on canvases, by material name), so there is nothing for KTX2 / `KHR_texture_basisu` to do and no transcoder is loaded.
- **Not done**: meshopt's lossy filters (`method: filter`: octahedral normals at 8 bits, ~17% smaller again) would change the shading, so normals stay at 10 bits. The glTF JSON chunks (node trees, extras, accessors: ~12 MB of the ~29 MB raw) are only gzipped with the bundle.

## Bundles

The bake leaves ~2,100 small files (parts/ and props/: 24.6 MB raw with the indexes, ~8 KB a pack). The game would need thousands of requests, so the last step of `npm run bake:models`, `tools/bundle_models.mjs` (library `tools/model_bundles.mjs`), packs them into **ONE container file, `assets/models/bundles/models.rtb`, which is the only form of the models the game loads** (3.26 MB gzipped, 24.6 MB raw, 2,086 files); the loose files stay on disk for the tools and tests only.

- **Which paths are in it** is a rule (`G.Bundles.bundleOf(path)`, js/modelbundles.ts): `props/**`, `scenes/*.glb` (the hangar: docs/hangar-data.md) and `parts/<id>/**` (indexes, packs, `parts/_shared/**`) are in; whole-gun files (`guns/*.glb`, which the game does not load) and the bake reports (`parts/index.json`, `coverage.json`...) are in no bundle. The bundle holds each file under its path relative to `assets/models/`, paths in byte order.
- **Container** (`.rtb`, "RTB1"): the bytes `RTB1`, u32le `tocLength`, the table of contents as UTF-8 JSON `{ "files": [[path, offset, length], ...] }`, zero padding to a multiple of 4, then the files back to back (offsets count from the start of that data). The file on disk is that container **gzipped** (level 9, header OS byte fixed to 255), because a static host cannot be trusted to compress an unknown type; the reader recognises gzip by its magic bytes and unpacks it with `DecompressionStream` (off the main thread; a raw container is read as it is). Deterministic: the same files give a byte-identical bundle, whatever order or parallelism the bake ran in (`bundle_models.test.mjs` checks it).
- **Manifest**: `bundles/manifest.json` is what the game fetches first: `{ "v": 3, "hash": <16 hex>, "size": <gzipped bytes> }` (~50 bytes), the hash being the first 16 hex digits of the sha256 of the `.rtb` file's bytes. `bundles/index.json` (`{ version: 3, name, files, bytes, gz, sha1, hash }`); `v` / `version` is the format of the files in it (`G.Bundles.FORMAT`: 2 = float32 positions, 3 = int16 positions, see "Compression" above), and a stored copy of another format is never used (the IndexedDB record carries it too) is for the tools. Both are written by `tools/bundle_models.mjs`; `--check` fails if the manifest is missing, malformed, or has a hash or size that does not match the file, if the bundle is missing, stale or has orphans, if another `.rtb` lies about, or if an index entry does not resolve.
- **Local bundle store** (js/modelbundles.ts): GitHub Pages serves everything with `max-age=600` and an ETag that changes on every deploy, so plain HTTP caching would revalidate the file on every visit and re-download it after every deploy. Instead, at boot the game fetches `manifest.json` with `cache: 'no-cache'` (the one request that is always made). If IndexedDB (`rt-model-bundles`, store `bundles`, key `models`) holds the bundle **with the same hash**, it is used with no further request; otherwise `models.rtb?h=<hash>` is fetched (the hash in the URL, so no stale browser or CDN copy can answer for a new hash), stored as downloaded (gzipped) with its hash, replacing the old record (any other key, such as an old per-platform bundle, is deleted). It asks `navigator.storage.persist()` (no prompt) and, under `?checkModels`, logs the store decisions and `navigator.storage.estimate()` to the console (`[bundles] ...`).
- **A first visit starts the download at once.** The manifest tells the hash, but the page's main thread is busy running the other scripts by the time its response is handled, which would hold the download back by hundreds of milliseconds. So the script, when `localStorage['rt-models-stored']` (the hash the store was last given) is absent, starts `fetch('models.rtb')` itself, synchronously, as the first thing the page runs. When the manifest arrives the bytes are verified against its hash (sha256, `crypto.subtle`); if they are not the current bundle (a stale cached copy), or the fetch failed, it is fetched again by hash. A returning visitor with the store never makes this request.
- **Failure modes**: no IndexedDB, private mode, quota exceeded, eviction, or any IndexedDB error -> the bundle comes from the network (a failed write just means it is fetched again next visit); a stored copy that fails to parse (bad magic, truncated, bad gzip) -> dropped and fetched again; manifest fetch failure or a malformed manifest -> the bundle is fetched revalidated (`no-cache`) and not stored. A failed download is tried three times (0.5 s, 1.5 s apart); after that `G.Bundles.state().phase` is `'failed'`, every `getFile` rejects (nothing retries per file), the menu shows the error and a Retry button, and `G.Bundles.start()` begins afresh.
- **Runtime** (`G.Bundles`): `start()` -> `Promise<boolean>` (the download; idempotent; on the page it is called when the script runs), `state()` -> `{ phase: 'idle' | 'loading' | 'ready' | 'failed', loaded, total, from: 'store' | 'net' | null, error? }` and `onChange(fn)` (the menu's progress), `getFile(path)` -> `Promise<ArrayBuffer>` (waits for the bundle, slices the file out), `getJson(path)`, `bundleOf(path)`, `loaded()`, `stats()`. `js/glb.ts` asks it for every pack (`G.GLB.load(url)` parses the ArrayBuffer with `GLTFLoader.parseAsync`), for each platform index and for the props; `G.Models.ensure(def)` / `assemble(def)` and the facade are unchanged for their callers. There is no fallback to loose files: a path that belongs to the bundle comes from it or fails. The highlights' export worker loads the same script (no autostart off the page: its first `getFile` starts the download, from the store when it can).
- **Check** (`node tools/bundle_models.mjs --check`, part of `npm run test:models`): every loose file that belongs in the bundle is in it with the same bytes; no entry without a loose file (orphan); every pack of every platform index and every prop resolves in it; every bundled pack is named by an index; the manifest describes the file; no other bundle. `tools/bundle_models.test.mjs` has a negative test for each, and the determinism test. The model tests (`tools/model_env.mjs` `loadGameWithModels`) load through `G.Bundles` as the game does.
- **Deploy**: `.github/workflows/pages.yml` bakes (cached on everything a bake or `js/modelbundles.ts` reads), tests, and publishes the site WITHOUT `assets/models/{guns,parts,props}`: only `assets/models/bundles/` ships (3.3 MB).
- **Measured** (browser pane, local server, ONE bundle; the machine was busy with other bakes, so read the shape, not the last millisecond): first visit (nothing stored): 2 requests, 3.26 MB, bundle in memory ~235 ms after navigation start (the download itself 31 -> 172 ms on localhost, then unpack: gunzip of 24.6 MB, TOC parse); returning visit (hash matches the store): 1 request (`manifest.json`, ~50 B), bundle in memory ~220 ms (IndexedDB read + gunzip; no download). Before this change (81 bundles, fetched lazily): boot fetched `_boot.rtb` (0.58 MB) and every other bundle only when a gun needed it or the hangar was entered (82 requests, 3.25 MB, ~1.9 s for all of them once started, then a main-thread parse of every pack in the background).
- **Boot freeze (profiled)**: before the menu answered, the main thread was busy with, in order: executing the page's ~60 scripts (about 270-320 ms, not model related), then `G.Game.init` (266-318 ms: `G.R.init` 36-47, `bindMenu` 23-35, and `menuBackdrop` 196-235 = `Level.generate` 36-42 + `Level.buildMesh` 160-195, of which `LightGrid.build` ~110 and `Furniture.build` ~90), then the first rendered frame (71-94 ms: the shaders compile on the first `render`). It was the level behind the menu, built inside `init`, not model loading. Fix: the backdrop is now built after the first paint, in two tasks, once the bundle is in memory (`G.Game.menuBackdropSoon`), so `init` is 60-75 ms and the page answers from ~100 ms after load; the 230-360 ms `buildMesh` task still happens but behind a painted, clickable menu. Remaining ideas, not done: a lighter backdrop level, or splitting `LightGrid.build` across frames.


## Per-part bake and assembly

Code: `js/glb.ts` (contract, validator, the planner `planBuild` and the assembler), `tools/model_parts.mjs` (the builds and the rules learnt from them), `tools/bake_parts.mjs` (the index, the checks, the files, sharing), `model_emit.mjs` (writing), `model_sweep.mjs` (the sweep), `check_model_cases.mjs` / `check_models_assembly.mjs` + `model_report.mjs` (tests, report images), `check_models_parity.mjs` (against an older bake). The contract text is above (**Per-part pieces**); this is how it works.

**The game loads guns only from baked glTF**, so `G.Models.assemble(def)` has to produce every valid build and `infoOf(def)` its info. A wrong-looking model is a bug here, not something the recipe papers over.

**Nothing combinatorial is baked.** Parts are fixed models (no part is resized for another; barrels of different lengths are different parts) and a piece is placed by adding up offsets, so the bake makes one file per PIECE (a part's shape on a platform) and the index carries each part's offsets and values and the few rules that combine them. The earlier bake made a pack for every combination of the parts that shaped a slot, tabulated `info` over every combination of the parts a leaf depended on, and built a build for each combination to fill them (166,156 builds, 46,642 of them only to cover combinations; 43,755 index entries); the per-part bake builds about 550 a platform (45,701 in all) and none for a combination.

**The builds** (`collectBuilds`, per platform; every one is a build of the recipe, `G.GunRecipes.display`): the sweep (the default and the loaded builds, every part of every slot fitted once from each: `model_sweep.mjs`); the same from two more bases (every slot filled with its last part; every optional slot empty), so each part is seen beside other parts too; each part that opens slots fitted once on each base, and every part of a slot so opened fitted once on the first build that opened it (and what those open in turn); for a piece no base has (an iron sight's front post, when the bases carry a red dot), one build that has it, swept the same way; for each info leaf, each part of a slot that changes it beside two parts of each other such slot (a foregrip that gives the support hand and a bipod that leaves it to the handguard look alike next to one barrel); the edge cases and regressions (`tests/`). Then what a rule asks for to be pinned down: each provider in each variant, each part of a pair beside the parts of the other that move the piece furthest each way, every pair of parts whose lengths fall between a threshold's last absent and first present difference.

**The rules learnt** (`learnPlatform`, `learnInfo`). For each tag: the provider list (the base, the mesh slot's own build slots, the anchor's slot first: the one under which each provider draws one shape and every absence is explained); the pieces; the slots that move it (two builds that differ in that slot only, the same piece placed apart; more, the fewest that explain every build, only if those do not); their offsets, solved exactly (sparse Gauss-Jordan elimination on the vertex moves); and, where the sum does not explain every build, a condition slot, a cap, a pair, a variant, a stretch or a threshold (below). For each info leaf: the slots whose part alone changes it; the provider order and the non-providers (the fewest providers that explain it); for each provider slot, the tag whose offsets it moves with, then its own offsets solved exactly from the leaf's values; else a max with one part's value. Whatever the rules cannot explain fails the bake, naming the tag or leaf and a build (a recipe that draws one piece from two parts must split it with `k.at()`).

**The checks** (`checkBuild`, the bake fails otherwise): every build the rules were learnt from and `MODELS_SAMPLE` (5) random others a platform (414 in all) are planned from the index by the game's own planner (`G.Models.planBuild`) and compared with the recipe: each piece (its capture build's meshes) moved and stretched as planned must be the build's meshes vertex for vertex (to 0.01 mm; float noise is 0.002 mm), and every info leaf the same (to 1e-8). So each piece is checked against every build it is in, each offset across the parts it applies to, and each rule across the builds it decides.

### The assembly rules (for any runtime: this is all of it)

The index is `assets/models/parts/<platform>/index.json` (the contract's **Per-part pieces** entry, `docs/gun-parts-index.schema.json`). A build is a map build slot -> part id; `<s>=<p>` names a part in a slot and `<s>=` the slot left empty (an empty slot can give offsets too). `A(s)` is `anchors["<s>=<build[s]>"]` (or nothing), `V(s, key)` is `values["<s>=<build[s]>"][key]`, else `values[""][key]`, parsed as JSON. Vectors are [forward, up, right] metres; a glTF point (x, y, z) is [forward, up, right] = [-z, y, x].

1. **Provider.** For a tag T: ps = the first slot of T.from that is filled in the build ("" if none or T.from is empty); q = "<ps>=<part>" (or "").
2. **Variant.** If T.vary = { by, key }: q += "#" + (build[by] ? V(by, key) as written in the index (the JSON text), or "null" : "none").
3. **Threshold.** If T.show = { a, b, gt } and not V(a[0], a[1]) - V(b[0], b[1]) > gt: T is absent.
4. **Piece.** e = T.pieces[q]; none: T is absent (the provider draws nothing of it).
5. **Offset.** r = the sum over every slot s of the index's `slots` except ps of A(s)["mount_<T>"]; plus, for each slot c of T.cond that is filled and each slot s other than ps and c, A(s)["mount_<T>?<c>"].
   - **Cap** (T.cap = { axis, by, of, op }): on that axis the `of` slots' terms are summed apart, into i, and r[axis] = (the rest) + (A(by)["cap_<T>"] defined ? op(i, it) : i), op min or max.
   - **Pair** (T.pair = { axis, h, by, op }): r[axis] = op(A(h)["pair_<T>"], A(by)["pair_<T>"]), either alone when the other is undefined.
6. **Stretch** (T.stretch; e has rear, len, len0): L = e.len0 + the sum over the slots except ps of A(s)["len_<T>"]; k = L / e.len; every point of the file first has its forward position f replaced by e.rear + (f - e.rear) * k (normals by the inverse transpose: k is along one axis), then it moves as in 7.
7. **Place.** Every point (mesh vertex, node pivot) of the file e.file moves by e.at + r. Nodes: a part_/group_ node's pivot comes from the piece that owns it (extras.owner, default true), else the first that has it; every other piece's meshes in that node are re-expressed against it; extras.parent nests nodes.
8. **Info.** For each leaf R of `info`: ps = the first slot of R.from filled with a part not in R.skip ("" if none); q = "<ps>=<part>" (or ""), + "#label" as in 2 if R.vary. v = R.own[q] (missing: the index does not cover the build, a bake bug); { "del": 1 }: the leaf is absent. If R.off[ps] (with R.vary and ps "", R.off[""]) exists and v is a number: v += the sum over the slots s other than ps of off.x["<s>=<build[s]>"] and, for each c of off.y filled, of off.y[c]["<s>=<build[s]>"] (s other than c). If R.max = { by, v: m } and m[build[by] or ""] exists: v = max(v, it). Leaves are paths (a/b/0) into the info object.
9. **anim and mounts.** info.anim: each piece's `nodes` (part_<key>: key -> node name). info.mounts: mount_<T> -> r for every placed T with r non-zero (informational).

## Pistols (the reform)

A pistol is built from independent parts with fixed interfaces, so each of its tags is drawn by one part and every other part only moves it (offsets; the one rule beyond the sum: the muzzle is the further of the slide's and a chassis's front). The recipe (`pistol()` in `tools/models/recipes.ts`; `len0` in the platform spec, `js/parts.ts` `pst()`) follows these rules:

| part | slot / tag | interface |
| --- | --- | --- |
| frame | `base` | slide rails, magazine well (`magAt`), light rail, grip seat: the same under every grip and slide (a chassis is built round it) |
| slide | `slide` (`part_slide`) | its own geometry (length, vent, compensator). Provides two anchors: its REAR (everything on it that does not reach the front sits at a fixed distance from there: rear sight, port, the optic cut at `0.32 x factory length`) and its FRONT (front sight, barrel exit). A longer slide extends forward only. |
| barrel | `barrel` (+ `barrel@slide`, the bore at the slide's mouth) | placed by the slide's front anchor; what shows (thread, match ring, crown) follows the barrel part, not the slide |
| muzzle device | `muzzle` | on the barrel's thread, moves with the slide's front |
| irons / dot | `optic` (rear sight, dot), `optic@slide` (front sight) | the rear sight and the dot are fixed distances from the slide's rear; the front sight is the slide's front anchor. Heights come from the FACTORY slide, so they never depend on the slide fitted |
| magazine | `mag` | the frame's well |
| grip | `grip` | the grip panels, or the chassis |
| chassis (`gr.pistol.chassis`) | `grip` (+ `fg`, `tac`, `tacL`, `optic`) | a frame-level part with an OPEN FRONT: built for the factory slide, so a longer slide comes out of the shroud; its grip is built round the frame's magazine well; it provides the rail (rifle optics), the side and under rails (lights, foregrip) and the SMG stock mount. With no rail sight fitted the slide's irons stay inside it |
| stock | `stock` (+ `stock@buttstock`, `stock@buttstock2`) | on the frame's lug; each part of an adapter chain draws its own piece, keyed by its own slot |

`tools/model_sweep.mjs`: a pistol's loaded builds use a threaded barrel (so the muzzle device and thread are in the reference builds and a slide change is seen to MOVE them), and the pistol chassis (so the foregrip, both side rails, the SMG stock and the magnifier are in them too).

## Authored pistols (Blender): the Maxim 9, the Welrod Mk II and the 2011

A pistol modelled in Blender uses the authored path (`models/<id>/<id>.glb` + `model.json`, platform spec `rcv: 'authored'`) with the **pistol anchor set** (the contract's *Authored sources* section above, `info.pistol`), seated by `authoredPistol()` in `tools/models/recipes.ts` (`pistol()` hands over to it for `rcv 'authored'` and is otherwise untouched). The built-in pistols are not affected, and each of its pieces is still drawn by one part.

- **What the model holds**: the frame (slot `base`), the slide (`part_slide`: slot `slide`, and the slot `optic` irons riding on it), the grip (slot `grip`), the barrel slot = the whole integral suppressor with its front sight, `part_mag`; a slideless pistol has `part_bolt` (the Welrod's knob, `info.anim.bolt`) instead of a slide. Anchors: required `mount_barrel`, `mount_mag`, and `mount_slide` with a slide; `mount_optic` (= `mount_optic_end`, the optic cut's centre and floor) when the platform has a pistol-sight slot, `mount_tac` when it has a light slot.
- **What is seated from the anchors**: a pistol dot (`S.minidot`, the same part as on any pistol) in the optic cut, riding the slide, replacing the model's irons; a light under the frame at `mount_tac`. Nothing is scaled. The platform's spec (`js/parts.ts`) names what it fits and the baker checks the anchors against it (`checkAuthored`: `mag` against `mount_mag`, an optic slot needs `mount_optic`, a tactical slot `mount_tac`, spec `bolt` against `info.anim.bolt`).
- **Variants (per-gun parts)**: every other `models/<id>/<name>.glb` is a VARIANT of the factory barrel or magazine, offered on that gun only (`GUN_MODEL_CONTRACT.authored.variants`: root `<id>_<name>`, `variant_json { gun, slot, of, info?, cap?, note }`). `js/parts.ts` `AUTHORED_PISTOLS` adds the part (`<id>.br.<name>` / `<id>.mag.<name>`, spec `model.avBarrel` / `avMag` = the file name) with the figures the game gives it; the recipe draws the variant's meshes in place of the factory ones. `model_cases` adds each variant alone, loaded and all together. **Suppression is the part's data, not hard-wired**: the part's `set` says `sup` / `device` / `can` (the Welrod's `bare` and `bare_long` barrels are `sup: false, device: 'none'`: loud, flash, and the sound is the unsuppressed report). **A variant can carry an optic cut**: its `variant_json.info.mounts.mount_optic` ([forward, up, right]: the cut's centre and floor) is where the recipe seats the pistol dot (any pistol dot, the authored Ember included, fixed on the frame of a slideless pistol), and its part `provides: { optic: 'op:pso' }`, so the optic slot exists only while that barrel is fitted (the baker checks the two go together, `checkAuthored`). The sources' text (variants included) is hashed into the bake's staleness check.
- **Manual cycling (the Welrod)**: platform spec `bolt: 1` (js/player.ts `boltGun`: the case stays in until the bolt is worked), vmanim `kinds()` gives a pistol with `o.bolt` the `'bolt'` action (the right hand takes the knob at `info.bolt`, which the baker takes from the middle of `part_bolt` when the model has none), `G.boltHold` is false for it. The bolt's stroke is `info.boltTravel` (metres, default 0.12 m for a bolt rifle): the model's when it has one, else the platform spec's `boltTravel` (the Welrod: 0.04); js/vmanim.ts moves the part_bolt, the knob and the hand that far, and the chamber view's bolt face follows.
- **Not on an authored pistol**: another slide, grip, pistol barrel, muzzle thread, chassis or stock (nothing in the model to hang them on; the platform has no such slots). The tritium night sights are excluded from the Maxim 9, the Welrod and the 2011 (their irons are the model's), and each one's factory irons (`<id>.optic`, on the shared `op:pso` mount) go on its own gun only.
- **A plain factory barrel (the 2011, `models/p2011`)**: `authoredPistol({ factory: { name, set } })` makes the factory barrel an unsuppressed one (`set: { sup: false, device: 'none', can: null }`) in place of the integral suppressor; a barrel entry with `same: true` is drawn as the factory barrel (no file of its own: the 2011's match barrel, a drop-in that looks the same). A threaded barrel needs a variant file with its thread (and a muzzle slot for it): the 2011 has none yet. The 2011's platform is made last (`LAST`, after the thermal sight: a part's id in a code is its place in the list). Its spec's `mag` is the model's `mount_mag` and `len0` its `mount_barrel` forward (the baker checks the first): a re-exported model re-derives them.

## Multi-barrel guns (Blender): the Tempest

The **Tempest** (`models/tempest/`, TASK 18) is an authored rifle (`rcv: 'authored'`, `js/parts.ts` `P('tempest', ...)`) whose six barrels are its magazine: a block of six bores with electrically fired, caseless, telescoped rounds, swapped whole on a reload. Two lengths of round fit its bores (the standard 10 x 31 mm, ten a barrel, and the rifle 10 x 53 mm, five), and the length loaded in a block decides how many it holds. Nothing in the code names it: a gun with `def.barrels` (js/data.ts) and a model with `info.barrels` is a multi-barrel gun, and a model with `info.hinge` has a reload that takes it apart. The rules are the contract's **Multi-barrel guns and reload sequences** section above; in short:

- **The model** (root extras): `info.muzzles` (one per barrel, in barrel order), `info.barrels` (`n`, `free_bore_mm`, `stack_mm`, `default`, and `rounds`: one entry per round type the block takes, each `{ round_mm, rounds_each, effective_mm }` with one effective length per round of a barrel, shortest first; the last is the same for every type), `info.barrelGroups` (`top`, `bottom`, `all`: indices into the muzzles), `info.modeDial` (the fire-mode dial: where, which axis, the modes in order, degrees a step), `hinge_json` (the reload sequence), a `display_ammo` surface. `models/tempest/model.json` says `sights.meshless` (the gun's own sights are the front-sight fin on the muzzle block, so there is no `optic` mesh) and `sights.railed` (the receiver's top is already a Picatinny rail: an optic stands on it with no rail piece of the recipe's). Authored guns may call their `info.anim` entries as they like (`front`, `latch`): what counts is the node each names and the node's own part key (`part_pump` is `pump`).
- **No barrel slot.** The platform has none: the bores are in the `mag` slot (the barrel block, with its carry handle), the muzzle block is the `muzzle` slot, and the handguard is the model's (arms with M-LOK, an I-beam whose bottom flange is a Picatinny rail), the only one it takes. `mount_barrel` is where the block seats (it need not be in front of the handguard); `mount_tac` / `mount_tacL` (the M-LOK arms) and `mount_fg` (the I-beam's rail) are the anchors a light, a laser and a foregrip or bipod hang from, `mount_stock` (the vertical rail at the back) the shared stocks'.
- **Nested part nodes.** `part_brk` (the forend, on a fixed hinge) holds `part_pump` (the sliding front with the muzzle block), which holds `part_mag` (the barrel block), which holds `part_carry` (its handle); `part_lever` (the latches) is the receiver's. The recipe builds them as nested groups (`partNode` in tools/models/recipes.ts: a node's meshes are placed against its own pivot and its pivot against its parent's) and the packs store each under its parent (`extras.parent`), so a pack of one slot (the muzzle's, the magazine's, the foregrip's) carries the nodes it sits in. What is clamped to the forend (a light, a foregrip) is inside `part_brk` and drops with it.
- **Variants of the muzzle.** `models/tempest/muzzle_<name>.glb` (`variant_json`: `slot: "muzzle"`, `info.muzzles` the six new muzzle positions) are the muzzle devices the gun takes, offered on it only (`tempest.mz.<name>`, spec `model.avMuzzle`): a six-bore suppressor, a flash hider and a compensator, drawn in the same node as the factory muzzle block so they slide forward with it. The platform's muzzle slot takes nothing else (no thread). Their figures are proposed in `js/parts.ts`.
- **The reload** plays `info.hinge` (`js/vmanim.ts` `hingeClip` / `hingePose`): the steps in turn over the first half (the old block comes out), a moment with it clear, then the same steps backwards (the new block goes in). Each step turns its node about the node's pivot (`rotate_deg`, three.js rotation about `axis`) or slides it (`move`, [forward, up, right], in the frame of the node named by `frame`). `lever`, `pump`, `brk` and `carry` keep their part keys but, on a gun with a hinge sequence, are moved by it and by nothing else (not by the shotgun's pump stroke or the break action's opening).
- **How the reload feels** is the steps' own optional data (`share`, `ease`, `over`, `back { share, ease }`, `hand { part, at }`: the contract's hinge row). The reload's length (`def.reload`, 4.5 s) is shared out in proportion: a lead-in (the hand to the gun), each step's `share`, a gap wherever the hand changes hold, the block away to the pouch and a fresh one back, each step's `back.share`, and the hand back to the handguard (`js/vmanim.ts` `hingeTimeline`). Each step eases by its `ease` (out) and `back.ease` (in) and the gun answers the ease (`hingeReact`): a `spring` kicks the gun back and up, a `detent` dips it with the effort (the hand pressing ahead of the part) and thuds on the stop, `heavy` sags it under the weight, `magnet` draws it a little forward and lets go softly. The support hand holds the point `hand.at` of its `part` and follows it as it moves (resolved after the sequence has posed the parts), and carries the block by its hold to the pouch and back. The Tempest's (build_tempest.py): the latches flicked up (`out`, 0.17 s, the thumb on their tab), the bail flipped up (0.19 s, the hand on its bar), the front shot forward by its spring (`spring`, 6% past and settled, 0.21 s, the hand under the forend), the forend pulled down against its detent (`detent`, 0.49 s), the block slid back and lifted out by the bail (0.13 s, 0.34 s), 0.41 s away; back in, the block set down and slid home (0.30 s, 0.13 s), the forend heaved up (`heavy`, 0.53 s), the front drawn home by its magnets (`magnet`, 0.38 s, a soft stop), the bail folded (0.15 s), the latches pressed down (0.13 s).
- **Firing** (js/player.ts `shoot`, js/data.ts `G.barrelsOf`, `G.pickBarrels`, `G.shotDef`): the weapon table's `def.barrels` (`n`, `mm0`, `mm1`, `groups`, `full`, `default` and `rounds`: for each round type its `per`, `cal` and sound `spec`) is the model's `info.barrels` and `info.barrelGroups` (the baker fails when they differ: types, counts, default, the ends of the effective lengths, the caliber and sound spec existing, and `mag` being the default block's capacity); the round type a gun's block holds is `w.rl` (a block item's `rl`), the rounds left in each barrel `w.bl` (`w.mag` is their sum, and a block's capacity is `n` x the type's `per`: `G.capOf`). A pull fires the barrels the mode asks for (`G.MODE_INFO`: low and high are full auto at 500 and 1200 rpm, double, triple and sextuple fire 2, 3 and 6 barrels at once): always the FULLEST barrels, ties to the lowest, so they empty evenly; the triple fires the top or the bottom group, whichever has more rounds left. A round's effective length is the loaded type's `effective_mm[rounds already fired from its barrel]`; its speed, damage (energy) and range are `full` (0.8) of the barrel's own at the shortest length of any type (`mm0`), rising to 1.0 at the longest (`mm1`), on ONE scale for every type (a given length of bore gives the same share whatever the round: the rifle round's first shot, at 296 mm, is already fuller than the standard's at 229), and its report is the synth's for that length (see the contract). Each barrel's round leaves its own muzzle, with its own error; a pull of several barrels kicks as the barrels' count to the 0.8 power.
- **Round types** (TASK 20; `def.barrels.rounds`, `CALIBERS`): the two lengths of round are two CALIBERS, `10/31` (10 x 31 mm caseless, 8 g, loads ball, hollow point, tracer) and `10/53` (10 x 53 mm, 9.8 g, loads ball, hollow point, tracer, sabot AP, buckshot), each with its own box, price and loads (`CALIBERS[cal].loads`: grams, muzzle speed at the longest effective length, pellets, sabot rod size; `.types`: the loads it takes, `G.ammoTypes(cal)`) and sound spec (`GUN_SPECS['tempest']`, `['tempest.rifle']`). A block holds ONE round type (`it.rl`), its capacity 60 or 30, and the gun's `w.rl` follows the block in it (`Gear.loadIn` / `exchange`); mixing lengths in a block is not possible (boxes are by caliber), mixing loads inside it is (as in any magazine). `G.shotDef` makes each shot's gun: that type's caliber (`rcal`, which `G.calOf` honours), spec, effective length, speed and range. Nothing else in the code names the Tempest: another multi-barrel gun with one round type just has one entry in `rounds`.
- **Display.** `display_ammo` is painted with one row per barrel and a pip per round left (`G.Viewmodel.paintAmmo`); the dial is turned to the selected mode (a marker the game puts on its face, until the model has a `part_dial`).
- **Found only in cases**: `caseOnly` on the weapon table keeps it out of the shop; it is a legendary (tier 4) and turns up in weapon cases from level 3 like the other legendaries.
- **Testing**: `tests/model-golden-tempest.json` (`node tools/check_authored_golden.mjs --update tempest`), the contract's negative tests (`tools/check_models.test.mjs`, "multi: ..."), and the baker's check that the weapon table and the model agree.

## Testing

Two separate steps, so CI can bake once and test separately, and a failed test never throws away a bake.

| step | command | does | never |
| --- | --- | --- | --- |
| GENERATE | `npm run bake:models` | runs the recipes and authored sources over a linear set of builds, learns who draws each piece, the offsets and the rules, CHECKS every one of those builds and a random sample of others (planned from the index by the game's planner) against the recipe, writes the pieces, indexes, props, bundles; fails on anything the rules do not explain | the edge cases against the golden fingerprints, the held-out set |
| VALIDATE | `npm run test:models` (= `node tools/check_model_cases.mjs`) | the contract and schema checks, the bundle check (`bundle_models.mjs --check`, `bundle_models.test.mjs`), then the edge-case suite, the regression cases and the golden fingerprints, on the baked files | write models (only `--update-golden` writes tests/) |

**The edge-case suite** (`tools/model_cases.mjs`, committed as `tests/model-builds.json`: platform, `why`, build). The cases are GENERATED by rules from the parts data (`G.Gunsmith`: `slotsOf`, `compatible`, `fitsSlot` with the build so the barrel/handguard length rule `fitsLen` applies, `prune`, `defaultBuild`), so a new gun or part gets cases without anyone writing them. About 13 per platform (pistols about 25), 1,059 in all. Per platform:
- `default`; `bare` (every optional slot empty); `loaded` (every slot filled with its first part: both tac rails, a foregrip, a red dot and a magnifier where they fit); `loaded-last` (the last part of each slot);
- the shortest barrel with the longest handguard that fits it, and the longest barrel with the shortest handguard;
- every part that OPENS slots (railmounts, buttstock adapters, riser dots, a pistol chassis, handguards that give rails, barrels that give a handguard or muzzle mount), fitted, with the slots it opens filled (an optic that only opens the magnifier slot is left to the sight stack);
- the sight stack: the lowest and the tallest optic alone, a magnifier behind the lowest and behind the tallest optic that takes one (height is ranked by sight type and its riser / dot / scope size);
- authored magnifiers: each one other than the first (which the rules above fit) behind the first sight that takes one, on the default build;
- pistols: each slide on the gun's own grip and on the pistol chassis, each grip under the gun's own slide, every one with a red dot (not the full cross, ~50 builds a gun);
- specials: integral suppressors, the biggest, the smallest and a drum magazine, a bipod, a suppressor on the muzzle.
Builds two rules give are one case carrying both labels. When the rules give something else (new part, new gun) the test fails with "tests/model-builds.json is not what the rules give": run `node tools/check_model_cases.mjs --update-golden` and review the diff of tests/. `node tools/model_cases.mjs` prints the cases per platform (`--list` with the labels).

**Regression cases** (`tests/model-regressions.json`, hand-maintained): every build that has ever assembled wrong, with a `why`. Add one whenever a model bug is found (a full build; the platform and `why`). A part id that no longer exists, or a build the gunsmith would prune, fails the test as STALE: map it to the current equivalent in the file and say so in `note` (the SR-25's handguard hg.ar.1 is now oem.hg.ar.10, for that reason).

**What is compared.** Each case is assembled from the packs (the real files, `G.Models.assemble`) and compared with the recipe; EVERY difference of a build is listed: triangles per slot, every info leaf, the animated parts and pivots, stale bounds. exact / within 0.05 mm / WRONG / NOT COVERED as before; any WRONG or NOT COVERED fails.

**Golden fingerprints** (`tests/model-golden.json`, committed): per case, per slot `{ tris, hash, box, area }` (hash of the triangles to 0.1 mm; box in mm; area in cm2) and every info leaf rounded, taken from the gun as assembled. They say what the gun IS whatever made it: once a gun is authored in Blender with no recipe to compare with, its cases are checked against the fingerprints approved before (a slot matches if its hash is equal, or its triangle count is equal, box within 0.15 mm and area within 0.2 %). `node tools/check_model_cases.mjs --update-golden` rewrites them (and the case list); the diff is reviewed in the commit. A case with no golden, or a golden with no case, is reported.

**The sweep.** The default and the loaded builds x every single part swap (about 9,100 builds, `model_sweep.mjs`): the base of the builds the bake learns from (with more bases: "Per-part bake"); `node tools/check_model_cases.mjs --sweep` assembles the whole sweep from the real files and compares with the recipe.

**Held-out random set.** `node tools/check_model_cases.mjs --held 10000` (`npm run test:models:full` with `--sweep`; `node tools/check_models_assembly.mjs` is the same with the cases off): random builds, 3 to 6 parts changed, seed 99001, never seen by the baker. Not part of the default test.

**Contact sheets.** `node tools/model_cases.mjs --sheet <dir>` writes `<dir>/index.html` and one page per gun: every case and regression, a side view of the assembled gun (one colour per slot, one scale per gun) labelled with its `why` and its build.

**Magnifiers on the rail** (`tools/check_magnifier_rails.mjs`, in `test:models`, about 4 s, nothing drawn; its tests `tools/check_magnifier_rails.test.mjs`). For every gun, from its default and its loaded build, every sight that opens the magnifier slot (in the optic or the riser-dot slot) with every magnifier: the build is made by the recipe with its feet log (`G.GunRecipes.feet(def)`), which records each rail the recipe builds (`S.rail`, an authored gun's own optic mount `mount_optic_rail .. mount_optic_rail_end`, or its railed receiver) with its span and top, the reflex sight's foot at its seat (`optF`, or `optFMag` with a magnifier: a red dot's riser, a holographic's base, a riser dot's riser, an authored optic's vertices on the rail top) and the magnifier's foot (S.magnifier: fSight - 59 mm .. fSight - 25 mm, at the tube's front whatever its length). The rail is the run of rails at the sight's top that holds its seat; a foot off its rear or front by up to 3 mm is a warning, more an error, unless the gun is in `tools/magnifier_rail_waivers.json` (`{ gun: { maxMm, why } }`: the guns that failed when the check came in, their overhangs up to maxMm warnings). No gun is waived now: 14 were fixed by a sight seat used only with a magnifier fitted (spec `optFMag`: mp7, m4, ar9, uzi, qbz95, tempest, mac10, fal, mpx, sr25, as the MP5's) or, where no seat fitted the sight and the magnifier on the rail, a longer rail (skorp `optRail`, p90, pocketgl, hailstorm: each now 133+ mm). A gun whose recipe builds no rail under the sight (it sits on an AK's cover, a round receiver, a mount of its own) is listed as unchecked.

**Adding a case.** A new KIND of case: add a rule in `generate()` in tools/model_cases.mjs. A build that went wrong: add it to tests/model-regressions.json. Either way, `--update-golden` and review.

**Timings** (24-core Windows machine, `-j 3`). The whole bake (`npm run bake:models`): 1 min 36 s, the platforms 1 min 23 s (before the per-part bake: 7 min 14 s and 6 min 36 s). `npm run test:models`: about 2.5 minutes, the suite itself about 2 for 2,463 cases + 9 regressions + golden. `test:models:full` (the sweep and 10,000 held-out builds against the recipe) is the occasional job.
